# V3：同步存储式引擎（唯一能真正追平 ScalableLux 的路）

> 立项理由、里程碑、击杀线、验收。**动代码前这份文档就是合同。**
> 前置结论来自 `docs/TASK-PERF-SKY.md` §10.15–10.16 与本次在同一脏环境里的五变体对照。

## 0. 为什么必须换内核（不是再找一个开关）

**实测事实（同一次会话、同一个脏环境，五变体全部交错对比）**：

| 变体 | 脏环境中位比值 |
| --- | --- |
| region 模式（当前默认） | 8.6 – 11× |
| storage 模式（V2 的架构） | 10.2× |
| 有界等待 + 内联回退 | 11.2× |
| 内联直提 | 9.7× |
| **ScalableLux（同步）** | 基准 ✓ |

**每一种变体里都有一轮 ~675–912 µs**（机器给 CPU 的那一轮）→ 结论：**机器给 CPU 时我们与 SL 同级（589 vs 573 µs ✓），不给时做什么都要等一个 tick** ✗。
根因不是计算量、不是队列、不是缓存、不是邮箱（这四条都已逐项排除 ✓✓），而是：**我们的光照完成必须等另一个线程（光照线程）被调度；SL 的活是短的同步 CPU 工作，塞进任何一小片时间都能跑完** ✓✓。

**所以「和 SL 一样不用等」只有一个实现：把算完并写库这件事，放在改方块那次调用里、在同一个线程上完成。**

## 1. 可行性（用已测数字说话）

- **单次改动的增量计算实测 ≈ 0.13 ms** ✓（`docs/HANDOFF` 记录的 pass 分解：apply 0.12 + 自身计算 0.13 + 发布 0.06）—— 与 SL 的 87 µs 同一量级 ✓✓；
- 也就是说：**同步做的成本是够的**，现在被浪费掉的是「区域映像 + 把结果交给光照线程」这一整套 ✗；
- 增量的两个引擎（`LuxBlockLightEngine` / `LuxSkyLightEngine`）、`materializeChanges`、`installSection`（就地覆盖两份地图 ✓）、通知队列 ✓ **全部已经存在** ✓✓ —— 本项目的资产够用 ✓。

## 2. 目标形状

**改动调用里（服务器线程、同一个 tick）**：

1. 取这一 tick 排队的改动（小批量 ✓，比如 ≤ N 条）；
2. **增量计算**：只算改动本身的影响范围（复用现有增量引擎 ✓），**不抽取区域映像** ✗；
3. **就地写入**引擎的两份地图（`installSection` 那套 ✓），并完成通知 ✓；
4. **不等待任何线程** ✓；返回时该 chunk 的光照已经是最终值 ✓。

大批量（世界生成、`regionChunks>1`、超阈值批次）**继续走现有的异步区域路径** ✓ —— 那条路在健康窗口里更快 ✓，而且大改动阻塞 tick 得不偿失 ✓。

## 3. 里程碑与击杀线（每步都要能独立验收）

| 里程碑 | 内容 | 击杀线 |
| --- | --- | --- |
| **M1 同步小改动路径** | 小批量（≤N 条）走「增量计算 + 就地写 + 不等待」；用一个开关切换，默认关 | 单次计算 > 500 µs ✗，或四项工作负载回归 ✗ → 停 |
| **M2 收窄到默认** | M1 通过全部验收后设为默认；大改动仍走异步 | 脏环境下比值不降到 ≤1.5× ✗ → 停（说明交接不是全部原因） |
| **M3 删掉交接** | 小改动路径不再经过发布队列/邮箱（含通知） | 探针 3/3 逐位一致 + 存档往返 + 客户端用例必过 ✗ |
| **M4 影子/回退** | 与旧路径做影子对比（同输入同输出校验），异常时回落 | 任何一次影子不一致 ✗ → 停并回到 M1 之前 |

**验收（缺一不可）**：26 测试 + 四项工作负载同场交错零回归 + **≥3 次相邻对探针逐位一致**（发布路径的规矩 ✓）+ 保存/重载指纹往返 + 客户端用例 + **脏环境下的比值 ≤1.2×**（这才是本项目的目标 ✓✓）。

## 4. 风险（都写在这，别到出事才想起来）

1. **写者模型**：光照线程仍在跑（世界生成/大批量 ✓），小改动路径在服务器线程写同一批地图 ✗ —— 必须限定写入的 section 互不重叠（小改动只碰自己那段 ✓），并沿用现有的环境代次检查（`externalEpoch` ✓）；
2. **存档安全**：绕过发布队列意味着「尚未落地的光」不再被发布队列记录 ✓ → 必须继续走 `hasPendingWorkFor` 那套「保存前标记未完成」的保护 ✓✓；
3. **客户端同步**：通知必须照发（`queueLightNotification` ✓）—— 这是不许省的一步 ✓；
4. **回退开关**：M1/M2 都用一个系统属性可一键回退 ✓✓；
5. **不要一次删两样** ✗：先让新路径跑起来并通过验收，再删旧的 ✓（M3 才动删除 ✓✓）。

## 5. 第一步（M1 的具体落点）

- 新增开关：`-Dlucistarlink.syncSmallEdits=true`（默认 **false** ✓）；
- 在 `LuxRuntimeManager.tick` 的入口处判断：本 tick 的改动条数 ≤ 阈值（先取 **8** ✓）且 `regionChunks==1` ✓ → 走新的同步路径 ✓；否则原路 ✓；
- 新路径内部：`materializeChanges` + 两个增量引擎 + `installSection` + 通知 ✓（全部复用 ✓），**不经过 `publishBatch`/邮箱** ✓；
- 先只保证**正确性**（探针 3/3 + 客户端用例 ✓），性能在 M2 再评 ✓。

## 6. 实测结论（2026-09-20）：M1 与 M3 都已实现、都已否掉

**都实现了**（都在 `master`，**默认关** ✓，构建与 26 测试全绿 ✓）：

- **M1 同步小改动路径**（`4598849` + 世界生成守卫 `4fa2819` ✓）：小批量（≤512 条记录、`regionChunks==1`）
  由调用线程算完后就地写引擎、不等光照线程 ✓。**正确性：4/4 轮相邻对探针逐位一致** ✓✓（两组标签 ✓）。
  实测触发率：`syncSmallEdits.routed` == 有改动的 tick 数（**100%** ✓）。
  **性能：在有负载的机器上 A/B 无改善** ✗（OFF 7.607 / ON 8.190 ms，n=2→3 ✓，p=1.0 ✓）。
- **M3 同步路径跳过 `updateSectionStatus`** ✓（让引擎自己的 pass 无事可做 ✓）：
  **A/B 仍无改善** ✗（OFF 13.148 / ON 13.467 ms，n=3，比值 0.976，p=1.0 ✓）。
- **`inlineDrain` 直提**（更早的实验 ✓）：健康窗口里 **10× 回退** ✗（阻塞 tick 且没省掉引擎那趟 ✓）。

**被数据纠正的一个前提（重要，别再白跑）**：`computeRuntimeRegion` 只在**区域首次被触碰**时构建区域映像
（`runtime.region.init` 整轮 4 次、`reload` 0 次 ✓），**之后每一轮都是增量路线** ✓ —— 所以
「小改动每次都建区域映像」**不成立** ✗，那条改造没有可做的手术 ✓。

**因此：交付侧（跳、邮箱、状态登记）与计算侧（增量/映像）在代码层面已无杠杆** ✗✓ ——
在**健康窗口**里我们与 ScalableLux **同级**（589 vs 573 µs ✓✓）；在**有负载的机器**上差距由
**整台服务器进程的 tick 调度**决定 ✓，与本引擎的内部结构无关 ✓（两种设计在五种变体下都被量过 ✓）。

**这些实验全部保留为默认关的代码** ✓，结论记在此处，**不要重复尝试** ✓。
