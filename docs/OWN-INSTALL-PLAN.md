# 自持安装层（Own Install）——立项、前置测量与熔断

* 立项：用户，2026-09-22（「开新立项：做"每改动当场算"的算法/存储层」「然后再叠加上 S1 的方法 一定得想办法成功！」）
* 本文件所在树 = **2.0 的 LS-V2 分支**（`E:\LuciStarlin\LuciStarlink-LS-V2`）
* 前序：`docs/OWN-SCHEDULER-PLAN.md`（S1 项目，熔断触发已撤；§9 给出互锁定性）

## 1. 目标（一句话）

在引擎口径的 `block_toggle_border` 上达到 **minPass ≤ 1.5 ms**（当前 4.3–5.4 ms，1.x 1.26–3.4 ms），且四档玩家口径不回退、指纹一致、无挂死。

## 2. 已知证据（决定了这次的做法）

| 事实 | 数值 | 来源 |
|---|---|---|
| 我们的引擎每 pass **真正做的传播工作** | **25–62 µs** | 按-pass 探针（拆/放档） |
| 每 pass 的**入队调用数** | 117–131（其中 ~100 是"票据已存在"的早退） | 同上 |
| 每 pass 的引擎口径读数 | 4.3–5.4 ms | 同上 |
| **"持有队列"不可行** | 与"任何阻塞式读区块都要求引擎 settle"互锁（挂死 ×3，线程转储定性） | S1 §9 |
| **"每改动跑一遍队列执行"代价过高** | 约 35 µs/次（95 次 ≈ 3.3 ms） | 实验 6 |
| 1.x 为何能赢 | **从不延迟**：调用内算完，完成信号是本地事件 | 归因 |

**结论（本次设计的立足点）**：不能延迟（会互锁），也不能每次改动都走队列执行（35 µs/次）。所以只有一条路：**在调用内当场算完并安装，且把"当场算"的成本压到微秒级**——即自持引擎实例、绕开池与队列的按次开销。

## 3. 设计（与 S1 的关系：S1 的完成语义保留，但不再是"延迟"）

1. **自持引擎实例**：我们的层持有线程限定的 `SkyStarLightEngine` / `BlockStarLightEngine` 实例并复用（不走池、不做 per-call 取还），这是把"35 µs/次"里最大的一块去掉的前提。
2. **调用内安装**：`blockChange` 的路径上直接传播 + 安装受影响的分区 + **本地标记完成**；不产生队列任务、不产生 future 等待。⇒ 完成信号天然是本地事件（这就是"叠加 S1 的方法"的正确形态：**完成语义相同，但因为它不再延迟，也就没有互锁**）。
3. **队列只留给批量与世界生成**（延迟在那里无害）：批量改动、worldgen 的光照仍走现有并发队列，保持活性保证。
4. **正确性契约不变**：光照真相仍是引擎自己的 nibble 数组；安装必须同时写 updating + visible（1.1.5 的教训）；通知按分区合并。

## 4. 前置测量（动大工之前必须做，本次先做）

把 4.3 ms 拆开，判断"自持实例"能省掉多少：

| 待测项 | 方法 | 判据 |
|---|---|---|
| `queueTaskForSection` 自身的开销（每 pass 117 次调用一共多少） | 给它加 1/16 采样的计时（新增 `queueTaskNanosEst`） | 若 ≈ 数毫秒 ⇒ 自持实例 + 绕开它是决定性的 |
| 引擎任务执行（`handleUpdateInternal`） | 已有 `runUpdNanos`（每 pass 25–62 µs） | 已知很小 |
| 等待/完成（future 链 + 光照线程调度） | 引擎口径 = apply→future 就绪；减去上面两项即得 | 若大部分在这里 ⇒ 必须本地完成 |

**这一步的产出**：一张"4.3 ms 的构成"表。**若 `queueTaskForSection` 不是主要项**，则本项目的核心假设不成立，按熔断放弃，不再动工。

## 4b. 前置测量结果：核心假设被否，项目按退出条款终止（2026-09-22 夜）

给 `queueTaskForSection` 加了 1/16 采样计时（`LuxProfiler.queueTaskSampled(Nanos)` → `queueTaskNanosEst`），在拆/放档逐 pass 读出（微秒）：

| 每 pass 构成 | measured pass 2 | pass 3 | pass 4 |
|---|---|---|---|
| **入队全部开销**（`queueTaskNanosEst`，117 次调用） | **30.4 µs** | **123.2 µs** | **107.2 µs** |
| 传播（`runUpdNanos`，1 次调用） | 23.0 | 29.5 | 25.9 |
| apply（harness，3 pass 合计 0.516 ms ⇒ 每 pass） | **~172** | ~172 | ~172 |
| **引擎口径读数（minPass）** | **4620** | ~4600 | ~4600 |

**结论：4.6 ms 里我们"能摸到"的一切加起来不到 0.3 ms**——apply 0.17 ms + 入队 0.03–0.12 ms + 传播 0.02–0.03 ms。**剩下约 93% 是完成路径的等待**：光照线程被调度 + future 就绪。

**对设计的影响（逐项否掉）**：
* **自持引擎实例**（去掉池的取还）最多省 ~0.1 ms 级的开销 ⇒ **救不了这一格**；本项目的立项前提**被实测否证**；
* 因此按 §4 的退出条款：**项目终止，不再动工**；
* 加上 S1 的结论（替换完成路径会挂死/互锁），这一格的完整结论是：**它不在我们能触及的任何一层**——不是算法、不是存储、不是调度、不是池、不是完成钩子，而是**底座"完成信号必须经由光照线程与 future"这一设计本身**。要改变它只能替换底座的引擎所有权（= 已关闭的 own-engine 方向）。

## 5. 预登记熔断（与 S1 同四条）

1. `block_toggle_border` minPass ≤ 1.5 ms（同会话 6 轮中位数）
2. 四档玩家口径不回退（每档 ≤ +5%，箱内判据）
3. 指纹与标准值一致（box `-40,32,-40,55,96,55`，`sky=905931078dfc5ace block=59e2252f732ce67b`，`chunksNotLightCorrect=0`）
4. 活性：不挂死、prepare 不超时、存档往返光照正确

## 6. 纪律（这次吃掉两轮的坑，已成文）

* 每次运行前：杀全部 java → `netstat` 确认 25565 空闲 → 开跑；跑完检查日志无 `BindException`；
* 一切改动带 `-D` 开关、默认关；熔断不过即整层撤回；
* 任何"延迟/持有"设计一律先问：**此刻有没有人可能在阻塞等引擎 settle？**（有 ⇒ 该设计不可行）
