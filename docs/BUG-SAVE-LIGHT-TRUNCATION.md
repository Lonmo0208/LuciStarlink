# 严重缺陷：重启后光照被截断成「只有发光方块自己那一格」

> **状态：已修复（1.1.5，2026-09-19）。** 证据链见文末「定位与修复」一节。
> 症状：**服务器每次重启**，世界里的光照都退化成「只有光源方块自己那一格」（荧石看着亮是它的贴图，周围一圈全黑）；
> 把方块挖掉重放就恢复正常，**但下次重启又坏**。1.0.3 起就存在（用户在 1.0.3 上首次报告）。

## 定位与修复（实测证据链，全部为「同一份世界、同名标签指纹逐位比对」）

复现与定位用的是数据包驱动的往返（`ls-border-scenario.sh gen|reload`，命令见下）：

| 实验 | 结果 | 结论 |
| --- | --- | --- |
| 引擎关闭（对照） | 三方块光指纹**逐位相同** | 往返本身没问题，块光指纹在这条场景里是可用判据 |
| 引擎开启（1.1.4） | 三组**全变**，天空光三组不变 | 差异是我们造成的 |
| 引擎开启 + `-Dlucistarlink.enableWorldgen=false` | 三组**逐位相同** | 元凶是**加载时的世界生成重算路径** |
| 引擎开启 + 新增闸门（1.1.5） | 三组**逐位相同** | 修复 |
| 运行期边界编辑探针 `ls-border-edit.sh`（我方 vs 引擎关闭） | `edit` / `edit_border` 两标签的 sky 与 block **逐位一致** | 运行期路径未受影响 |

**根因**：`lightChunk` 注入**没有区分**「区块自称光照已完成」与「真正新生成」。从盘上加载、带着自己光照的区块
（`isLightCorrect() == true`）也被我们重算 —— 而加载时序里引擎还没有那份光照可作为传播基线，算出来的就是
「只有光源自己那一格」的坏场，再**盖回**盘上正确的那份。于是每次重启都毁一次数据。

**修复（1.1.5，两处）**：
1. `lightChunk` 注入加闸：`chunk.isLightCorrect()` 为真时**不接管**（盘上的光照是权威的）。世界生成出来的区块是
   `false`，照旧走重算 —— 所以世界生成的光照不受影响（旁证：修复后世界生成场景的天空光指纹与引擎关闭基线逐位相同）。
2. `publishDirect` 同时写入 `visibleSectionData`（发包与序列化读的那份），不再依赖引擎自己的更新周期去提升
   `queueSectionData` 写入 `updatingSectionData` 的数据。

**验收已经达到**：`gen → reload` 三标签方块光指纹逐位相同；26 个测试全绿；运行期边界编辑探针与对照逐位一致；
产物元数据 `incompatible`（`dist/lucistarlink-1.21.1-1.1.5.jar`，
md5 `27d26dc61da1b40f10ff868b3ceca0bd`）。

**对已经坏过的世界**：盘上那份已经被写坏了，1.1.5 不能凭空变回来 —— 用 `/lucistarlink relight 256` 分区域修一次，
之后重启就不会再坏（这才是这一版真正要验证的事）。


## 这条信息推翻了什么（不要再沿旧思路查）

- ❌ 不是「世界上一次被 ScalableLux 保存、我们没重算」——那是**一次性**的，不会每次重启复现；
- ❌ 不是客户端没收到光照包——F3+A 重载区块无效；
- ❌ 不是 `relight` 命令、不是 `forcePublishIdentical`、不是 `forceLightIncorrectOnSave`——它们都只是暂时性手段；
- ❌ 不是「拆放方块有效」能解决的——那只是把**内存里**的光照修对，**写盘那一份仍然是坏的**，所以重启即复发。

**结论：我们模组的保存（或区块卸载写回）路径，把光照数据写成了坏的那一份。**

## 首要嫌疑（按怀疑度排序）

1. **写回时读的是哪一份数据**。我们自己的注释就写着：引擎的游戏内光照读 `updatingSectionData`，
   而**区块包与序列化读 `visibleSectionData`**，两份都必须拿到数据。默认路径走 `super.queueSectionData(...)`
   （两份都写），但 `directSectionInstall` 分支走 `lucistarlink$installSection(...)`——**必须确认那条路同样写了两份**，
   并且**就地覆盖 `DataLayer`**（绝不能替换对象：光照线程仍在往它持有的那个对象里写）。
2. **未脏即不发布**：我们只发布变脏的 section。存档/卸载时要写回的 section 如果从没被我们发布过，
   它写回的是引擎里的旧数据——**需要确认那个"旧数据"是不是我们从没同步进去的那一份**。
3. **区块卸载写回**：`load`→`unload` 是常态（玩家走动、`/forceload`），比"显式 save"频繁得多。
   现有 `ls-border-scenario.sh gen|reload` 的存档往返是**通过**的，说明小场景没问题——
   **复现必须包含"走远让区块卸载"与"大量光源"**两个要素。

## 复现步骤（三步，必须先在单机复现再动代码）

**实测补充（2026-09-19，本轮尝试的记录，别再踩）**：`clientcase.sh up` + `cmd` 这条路**注入不进去** ——
FIFO 写了命令但服务器日志里连命令回显都没有（没有 `setblock` 反馈、没有指纹、也没有报错），
这与早先记过的坑一致（该脚本的服务器控制台读取线程在启动时就没有读者）。
**因此复现必须走数据包驱动的链路**，也就是现成的：

```
SCENARIO_KEEP_WORLD=0 bash ls-border-scenario.sh gen rt1     # 放光源、采样指纹、save-all flush、停服
bash ls-border-scenario.sh reload rt1                        # 起同一份世界，再采一次同样的标签
```

`gen` 与 `reload` 同名标签的指纹必须**逐位相同**；不相同即复现成功。**注意**：早期版本的小场景往返
是**通过**的，所以这轮复现必须加入两个要素才能命中：**① 大量光源**（不是一两个）、
**② 区块被卸载后写回**（走远 / `forceload remove` 之后再停服）。

1. 起服（我们的 jar）→ 放几个光源（荧石、火把各一）→ 确认光照正常；
2. `/stop`（或 `/save-all flush` 后停）；
3. 再起服 → 看那片区域的光照。若退化成"只有自己那一格"，复现成功。
   **加强版**：先走远让区块卸载再停服；或在 `ls-border-scenario.sh gen` 与 `reload` 之间加入 `/forceload remove`。

## 验收

- 重启前后同一区域的**光照指纹逐位相同**（用现成的 `/lucistarlink dumplight`：`gen` → `reload` 两个标签必须相等）；
- 该指纹测试要覆盖**卸载过的区块**和**多光源区域**；
- 在修好并通过上述验收之前，**不要在生存/生产服务器上使用本模组**（每次重启都会损坏一次光照，
  而重放方块的修复会在下次重启时再次被抹掉）。

## 给用户的即时建议

先回退到 ScalableLux 或原版跑生产，等这条修好、并且我们用「重启前后指纹一致」证明之后再换回来。
