# V2 功能线：客户端光照接管（设计 + 实施顺序）

## 0. 当前状态（2026-09-19）

**第 1、2 步已实现并已提交**（`master`，版本号 1.2.0 未发布）：

- `LuxClientLightProbe` + `ClientLightEngineProbeMixin`（只读统计，`-Dlucistarlink.clientProbe=true` 才输出）；
- `LuxClientLightEngine` + `ClientChunkCacheMixin`（`ClientChunkCache` 构造函数里的唯一构造点，
  `-Dlucistarlink.clientLightTakeover=true` 才换成我们的子类，否则原版引擎）；
  子类**只**空实现 `checkBlock` 与 `propagateLightSources`，`runLightUpdates` / `queueSectionData` /
  `updateSectionStatus` 保持原版 —— 它们是数据管线（`queueSectionData` 同步写存储、`runLightUpdates` 负责提升到
  可见层，跳过它会把客户端光照冻住，正是 1.1.5 在服务端修过的那个坑）。
- **已验证**：构建通过、26 测试全绿、**开发客户端完整启动且 0 个 mixin 应用失败、0 异常**
  （这道闸是必须的：客户端 mixin 应用失败会让每个客户端启动即崩）。
- **未验证（下一步）**：开启接管后**在世界里**的行为 —— 需要按 §6 跑一轮
  `clientcase`（`ls-border-edit.sh ... KEEP_SERVER_RUNNING=1` + `runClientMultiplayer`），
  用探针数值证明「服务端送来的 section 数据远多于客户端自己的重算」，再截图验证光照与帧时间。

> 背景：`V2`（全局存储架构）已收线（`docs/V2-CONTINUATION.md`），这条是**下一个大版本的功能线**。
> 客户端光照接管是我们在与 ScalableLux/Starlight 的对比里唯一明确写着「未做」的维度，也是唯一还能给用户
> 带来**体感**收益的未做项（省客户端 CPU/内存 + 两端光照同源）。

## 1. 目标（按收益排序，写清楚才好验收）

1. **客户端不再自己算光照** —— 光照数据由服务端发来（现在就已经是这样），客户端只负责**存与查**；
2. 客户端与服务端**同源**，消除「两端算法不同导致的边缘闪烁/不一致」这类问题；
3. 在低配机/大视距下，客户端每帧的光照开销与内存占用下降。

## 2. 关键设计选择：**保留原版的数据结构，只跳过客户端的重算**

这是整个方案里最重要的一条。客户端渲染读的是 `LevelLightEngine` 的
`getLayerListener(layer).getDataLayerData(sectionPos)`（以及 `ChunkAccess` 上的 `DataLayer`）。因此：

- **不替换**数据结构、不替换读写入口 —— Sodium / Embeddium / 光影都直接读这些结构，换了就是兼容性地狱；
- **只接管**「客户端什么时候、为谁重算光照」这一件事：把客户端那台光照引擎换成一层薄封装，
  它把服务端送来的 section 数据照原样放进去，**跳过原版那套增量传播**（客户端的传播本来也只是在补
  服务端没发全的部分 —— 而那部分我们服务端已经算好了）。

这样即使某台客户端上出现了我们没想到的时序，最坏结果是「光照和原版一样」，而不是黑屏。

## 3. 数据流（现状，已工作）

服务端发布 → 通知 → 引擎把最终数据放进 `visibleSectionData` → 区块包/`ClientboundLightUpdatePacket` →
客户端 `ClientPacketListener` / `ClientChunkCache` 把数据交给客户端光照引擎 → 渲染读取。
我们的服务端那半已经验证过（客户端用例通过：边界改方块，客户端立即变亮），
所以这一条线要做的是**客户端那半的最后一步**：别让它再自己算一遍。

## 4. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 与 Sodium / Embeddium / 光影冲突 | 见 §2：不动数据结构；先做"只跳过重算"的最小接管；每一项都要有共存验收 |
| 客户端拿到不完整数据（丢包/部分更新） | 缺数据时**退回原版路径**（按 section 判断，不做全局开关） |
| 切维度 / 切换世界 / 断线重连时的生命周期 | 单独一组验收（`LevelLightEngine` 随 `ClientLevel` 重建，必须确认我们的包装一并重建） |
| 渲染线程被拖慢 | 我们的路径只做「写入 + 返回」，不做计算；用帧时间前后对比证明 |

## 5. 实施顺序（小步走，每步都能独立验收）

1. **客户端探针（只读，零风险）**：统计客户端光照相关耗时与调用量（光照引擎的 `runUpdates`/`checkBlock`
   调用次数、每帧耗时），作为"接管前后"的对照基线。同时确认客户端光照数据确实来自包、而不是本地重算。
2. **最小接管**：客户端光照引擎换为薄封装（存服务端数据、跳过增量传播），**默认关闭**，用一个系统属性打开。
3. **边界情况**：切维度、切换世界、断线重连、区块重载（F3+A）、服务端发部分 section 更新时只发变化的部分。
4. **共存与压测**：与至少一个光影/优化模组共存；大视距长时间跑，看帧时间与内存。

## 6. 验收（缺一不可）

- ① 同场景下客户端与服务端光照数据一致（服务端用 `/lucistarlink dumplight` 采指纹，客户端侧用探针统计同 section 的字节）；
- ② 现有客户端用例复跑通过：边界上放/收光源，客户端**立即**更新，不需要重载区块（方法见 `docs/HANDOVER.md` 的客户端小节：全分辨率 F2 截图，桌面截图不算判据）；
- ③ 帧时间不劣于接管前（探针数据对比）；
- ④ 与 Sodium/Embeddium 至少一个共存不崩、光照正常；
- ⑤ 断线重连、切维度、F3+A 各自一轮不崩、光照正确；
- ⑥ **服务端四项工作负载零回归**（同场交错 ≥5 轮）。

## 7. 明确不做

- 不替换客户端的数据结构、不替换读写入口（Sodium/光影兼容的底线，见 §2）；
- 不在客户端重算光照（那是我们正在删掉的东西）；
- 不为了性能去动服务端已有的发布/通知路径（客户端用例与指纹验收都建立在它之上）。
