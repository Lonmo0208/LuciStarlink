# 缺陷：世界生成的自然光源光照不对（「摸一下才亮」）

> **状态：已修复（社区 PR #1，作者 lbw14514；合并提交 `9bbb6fe`，修复提交 `eb28b8e`…`a50f9e8`）。**
>
> 症状：**自然生成的光源**（村庄/废弃矿井的火把、岩浆湖、下界的荧石与菌光体）周围的光照不对 ——
> 看着发暗，或者光穿过墙壁照到不该亮的地方；**在附近放/拆一个方块就恢复正常**，但没走过去的地方一直不对。
> 这条缺陷从 1.0 起就在（用户 2026-09-20 报告：「世界自然生成的火把！发光有问题 得手动刷新」）。

## 根因（两条，都会让那片光照停在错的值上）

### 1. 世界生成算光时把邻居区块当成了空气（halo 材质缺失）

我们的光照图像把「自有区块 + 一圈 halo」一起算，而 halo 的**材质**（不透明度/发光）是按需物化的：
`lazyHaloLight` 模式下只有**运行期批次的改动集合**会驱动 `materializeReach` 去补。
**世界生成没有改动集合**，所以 halo 材质一直停在初值 0 —— 0 就是空气。后果两步：

1. 传播把邻居的石头、泥土、水当空气 → **光穿墙**（本该被挡住的光漏过去）；
2. `worldgenHaloPublish` 默认开启，这份算错的 halo 光照被**发布进邻居区块**，
   把邻居已经算对的光盖掉。

玩家看到的「摸一下就好」：放/拆方块走的是**运行期**路径，那条路径有完整的材质物化机制
（`materializeReach` 按改动集合补 halo），所以一碰就修回来。

### 2. 世界生成往「已经加载」的邻居区块写方块时，光照更新被吞掉

结构/特征跨区块时会把方块写进**已经生成、正在 tick 的**邻居区块（`ServerLevelMixin` 的判据就是
`FullChunkStatus.BLOCK_TICKING`）。这条写入路径上：原版 `checkBlock` 被我们接管（取消），
而运行期入队又被「世界生成写入压制」（`WorldgenWriteScope`）挡住 → **既没入队、也没让原版处理**，
那片光照就永远停在旧值。这类改动不在生成中区块自己的整块计算覆盖范围内（它算的是自己那张图像）。

## 修复（PR #1）

- `extract` / `populate` 增加显式 `lazyHaloMaterials`：**两条全量重算路径（世界生成、`/lucistarlink relight`）
  传 `false`**（完整提取材质，含 halo）；运行期保持 lazy（它有 `materializeReach` 那套机制）。
  首次区域初始化时若「采纳引擎光照」不可用，会再全量提取一次再算。
- 唯一一处 `populate` 全清材质改成**按提取范围清零**（`clearMaterialsForChunks`），物化标记与提取范围
  严格对齐（`markRegionLightMaterialized`），并让 `beginFullPopulate`/`resetForReuse` 一起失效标记 ——
  标记留着不补，等于宣告「那片材质是对的」，光就会穿墙。
- 世界生成的材质提取**挪进同一个 worker 线程**（每区块约 5.6 ms，9 个区块的方块扫描），不再卡区块生成线程。
- `enqueueBlockChange(Level, …)` 不再受世界生成压制；队列满丢改动时置标志、由 tick 转成背压窗口
  （以前是静默丢弃，`hasPendingWorkFor` 也看不到它们）。
- 另有 5 处并发/记账修复：`RuntimeUpdateQueue` 入队移进 `compute` 的 bin 锁；
  `RuntimeRegionState.drainExternalSections` 整组 CAS 替换（复制+removeAll 会丢同一个 section 的第二次标记）；
  `RegionLightData.resetForReuse` 清物化标记；`scheduleRegion` 准备段抛异常时回滚 owner 与 `scheduledRegions`
  （否则该区域永远留在 `scheduledRegions`，后续改动全卡死）；Sable 在场判据统一到「标记类是否存在」。
- 世界生成在飞作业上限 `workerCount × 2 → × 4`（材质提取进了任务，任务更长）；
  删除废弃的跨区 boundary-delta 原型（默认关的死代码）。

## 实测证据（本次审查，2026-09-20，同一台机器）

### A. 下界顶棚带：天然荧石/菌光体的光照必须与原版逐位相同 ← **决定性的一条**

场景：同一份种子（12345）、净下界、`randomTickSpeed 0`、`forceload` 0..63×0..63（16 区块）、
顶棚 y=100..125 采样 102,400 格，等引擎静默（`dumplight` 自带 20 tick 静默判定）。
参照 = **同一个 jar** 加 `-Dlucistarlink.enableWorldgen=false`（走原版引擎）。

| run | `ceiling`（64×64）block | `ceiling_narrow`（32×32）block |
| --- | --- | --- |
| 修复后 | `543a8d1f6d6e6847` | `3bc44605ff1713c6` |
| **原版（参照）** | `543a8d1f6d6e6847` | `3bc44605ff1713c6` |
| 修复前（`c46ecfc`） | `5dbe73c282d5567e` | `55dc0ebb67c817b3` |

天空光三组都是 `5125674880996325` / `46e5dd35c3bff325`（净下界的天空光恒 0）——
与旧结论一致：这一带的天空光本来就是对的。
**修复后与原版逐位相同；修复前与原版不同** —— 缺陷在装置里复现了，修复把它按平了。

逐格对照（y=110，x=0..31，z=0）看得最清楚：

```
原版      block=33432234566543210000000000000000
修复后    block=33432234566543210000000000000000
修复前    block=23432234566543210000000123456789
```

`x≥24` 那段 `123456789` 就是**光穿过区块边界、穿过实心方块漏进来的**（本区块的方块在邻居那张图像里
被当成空气），最左边一格 `3→2` 也是错的 —— 玩家看到的就是这个「光穿墙」。

### B. 已经发光的地方，相邻区块生成后不能被改坏

场景：`forceload` 一片、放三个光源（荧石×2 + 火把）、采指纹、再 `forceload` 隔壁让它生成、再采一次。

| run | before | after |
| --- | --- | --- |
| 修复后 | sky=`8364153b00ee7dbe` block=`3281f74e1cfab130` | **逐位相同** |
| 修复前 | sky=`8364153b00ee7dbe` block=`3281f74e1cfab130` | 逐位相同 |

**这条两个 jar 都通过**：新生成的区块里没有天然光源，即「halo 材质当空气」在这条场景下没有可用的
发光体去暴露它 —— 它只说明发布没有做多余的事，**不能**证明修复的必要性；证明第一条的是上面的 A。
两个 jar 的绝对指纹还完全相同，说明这条装置本身是可复现的。

### C. 构建与单元测试

`./gradlew build` → **38 个测试 0 失败**（新增 `RegionLightDataMaterializationTest` 8 例、
`SectionFaceMaskTest` 5 例）。dev 服 + dev 客户端在新构建上跑过真实会话，日志无异常。

## 对已经坏过的世界

盘上那份光照已经被写坏，而且区块自称「光照已完成」，所以我们不会重算它。用
`/lucistarlink relight 256` 分区域修一次即可；修完以后再生成的新区域不会坏。

## 仍未解决 / 需要单独验证（不要当成已修）

1. **运行期「全量重算」路径仍是 lazy halo**（作者有意保留：改成全量提取会让 `structure_cube` 慢 38–47%，
   理由是该区域已经初始化过、halo 留着上一次的材质）。同一类「材质当空气」的隐患在这条路上可能仍然存在，

   因为那条路径会把改动集合清掉、`materializeReach` 因此看不到它。需要单独探针：大 `/fill` 骑在区块边界上，
