## 1. 我接受/确认的结论（此后不再讨论）

1. **验收口径改为 per-pass 最小值的中位数**（读 `lucistarlink-light-benchmark.jsonl` 的 `minPassNanos`），≥5 次重复，所有引擎一视同仁；
   旧的"wall ≤ 3.0 ms"作废（wall 是 tick 量化后的量，无区分度）。当前约定线：**per-pass min 中位 ≤ 1.0 ms**。
2. **`directSectionInstall` 保持关闭**。你的数据（0.599 vs 默认 0.651，噪声内）加偏差率，足以否掉我"直装=解法"的判断。
3. **原地覆盖是硬要求**：`DataLayer` 对象身份有意义——光照线程还在往旧对象写，换对象等于把它的写入送进孤数组且无人重算
   （你实测 3 次里 1 次偏离 vanilla，原地拷贝 0 次）。此条必须写进 ARCH-V2 阶段 2 与风险清单。
4. **piggyback 已否决**（per-pass min 0.48 → 1.24 ms + 14.6 ms 卡顿）——起因是触发等 vanilla 的 `tryScheduleUpdate`，
   而私有 drain 的 250 µs 定时器更及时。**"在同一轮提交"不是收益点，"及时"才是。**
5. sorter-mailbox 回调本来就在光照线程上 → 再挂任务是队列跳，不是线程唤醒。
6. **block 光偏差已定性**：可复现、根因是对象替换，不是随机竞态；此前的两次撤回记录保留，新的"原地覆盖"结论为最终版。

## 3. 下一轮动作（按顺序，前一项不达标不进下一项）

### 动作 A（首选、成本最低）：把"及时"做到位——去掉小批次的合并延迟
你的结论是"being prompt is the win"。那就直接攻这一点：
- 对小批量（`runtime.inlineBatchChanges` 覆盖的规模）**跳过 250 µs 的 `publishCoalesceNanos`**，或把 drain 触发改为"发布即投递一次"，
  保留私有队列与光照线程写入（**线程归属不变**，风险最低）；
- A/B：per-pass min 中位（≥5 次）+ wall，对照组为当前默认；
- 判据：per-pass min 中位 ≤ 0.593 ms（追平 SL）或至少显著下降且无回归。

### 动作 B（备选）：服务端线程内联"算 + 装"的完整形态
你之前测的"内联"只内联了**计算**，发布仍走邮箱——那不是 ScalableLux 的形态。完整形态是**同一线程内算完就装**。
但注意原版存储是**单写者（光照线程）**：
- 如果从服务端线程原地写，会与光照线程在同一层上的写入竞争（层内撕裂风险）→ **必须先用探针证明无偏差**（≥3 次 0 偏差）才允许考虑；
- 更稳的折中：内联计算 + 立刻把安装作为一个**引擎任务**投递（保持光照线程写入），只是触发要**及时**（与动作 A 合流）。
- 我的建议：先做 A；A 不够再评估 B，且 B 必须带"偏差探针 0/3"的门槛。

### 动作 C：补完四档 per-pass min 对照表（≥5 次）
目前只有 `sky_hole` 一档有可信数据。四档都要出（我们 / ScalableLux / vanilla；Lucis 2.0 单独用它的 harness）。
只有这张表齐了，"四档全胜"才有依据；也才能决定 `directSectionInstall` / `worldgenHaloPublish` 的默认值。

### 动作 D：ARCH-V2 落三处修正 + 一处新增
1. 阶段 2 的"提交怎么调度"必须重写：piggyback 已实测否决；**及时性是关键变量**；写入只能发生在光照线程；
2. 风险清单新增/强化：**必须原地覆盖，禁止替换 `DataLayer` 对象**（附你的实测：3 次 1 偏离 vs 0）；
3. 线程模型更正：mailbox 回调已在光照线程；
4. 新增一条："任何触碰安装/发布路径的改动，必须附偏差探针 ≥3 次 0 偏差"。
