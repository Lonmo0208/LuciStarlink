# 缺陷（未修）：跨区块边界的「减少光照」不收敛，残留亮光会写进存档

> **状态：已复现、已定位机制、**未修复**（2026-09-20）。** 触发条件是用户实测出来的：
> **大范围 `/fill` 荧石 → 空气 循环，停在「空气」这一步**。当场（客户端）看着是黑的，但**保存退出重进**后
> 会出现残留光源。证据链与两次失败的修复尝试都在本文，避免后人重复这些弯路。

## 症状与判定

- 内存里：引擎（服务端）那份光照**没有把被清掉的光减下去** —— 逐格看是「**改动格自己变成 0，周围那一圈
  14/13/12… 的旧光还在**」（一片圆顶），见下面的平面数据。
- 客户端当场看不出问题：**客户端自己的光照引擎会按收到的方块变化把光算黑**，而服务端没有把「变暗」的结果
  发下去，所以当场是黑的。
- **重进后才暴露**：重进时客户端按服务端那份光照绘制 → 残留亮光出现。
- 存档为什么会有：区块自称「光照已完成」，`ChunkSerializer` 写盘读的就是引擎这份（`visibleSectionData`）；
  我们只在「该区块还有未完成的工作」时才强制标成光照未正确（`shouldRelightOnLoad`），
  **工作排空之后才保存的存档，就把这份残留写进盘里了**。所以「重进就坏」和「重进反而好了」都可能出现 ——
  取决于保存那一刻引擎里还有没有挂着的任务（本次探针里恰好挂着一个，于是重进被重算、反而正常）。

## 复现（`mc-smoketest/ls-refill-probe.sh`，单机、可重复）

场景：同一份种子、`randomTickSpeed 0`、`forceload` 80..111 × 80..111（4 个区块）、
`/fill 80 120 80 111 120 111 glowstone` → `air` → `glowstone` → `air`（每个状态都采指纹 + 逐格平面），
然后 `save-all flush` 停服，再起一次同一份存档采同样的标签。

| 阶段 | 标签 | block 指纹 |
| --- | --- | --- |
| gen（内存里） | `large_air2` | `45b3fe947d9ab5cd`（**残留**） |
| reload（重进后） | `large_air2` | `b93a0c83ce3b6325`（全黑 ✓，被重算修好了） |
| gen | `small_air2`（8×8 单区块对照） | `2d3e9d3ae7775095` |
| reload | `small_air2` | `d80ac658736bb725` |

逐格对照（y=120，x=80..111，z=80）：

```
空气状态、内存里：  sky=ffffffff... block=00123456789abcdedcba987654321000   ← 残留（圆顶）
空气状态、重进后：  sky=ffffffff... block=00000000000000000000000000000000   ← 正确
```

`sky=ff…`（15）证明**方块确实是空气**（荧石会挡天光），所以亮的不是方块，是**没被清掉的光**。

## 机制（加了临时计数器后钉死的）

计数器（`LuxBlockLightEngine.applyRuntimeChanges`，临时的，已删）：

```
blockLight changes=256 seeded=256 zeroed=14118 adds=6439 sumBefore=3840 sumAfter=2345 fastEligible=false
```

- `changes=256`：一个区块组的批次大小（fill 跨 4 个区块 → 每组各 256）；
- `sumBefore=3840`（=256×15）：**改动格本来是有光的、衰减也排进队列了**；`zeroed=14118`：清除波确实跑了；
- `sumAfter=2345 ≠ 0`：**整段处理完之后，那些格子的光又被点亮了 ~9 格** —— 这就是残留。

重新点亮它们的是「**独立光源**」规则：`tryRemoveNeighbor` 里，邻居的光**不低于**被移除的等级时，就认为
「它的光不是从我这来的」，把它当作独立光源重新传播（这条规则本身与 vanilla 一致）。而这里是
**一大片同等级的光源被一起移除**：跨过区块边界那一侧邻居（属于**别的区块组**）在我们这张图像里还是
「15 的荧石」，于是被当成独立光源、把刚清掉的区域又点亮。

两个放大因素：

1. **区块组之间只通过「引擎里的光照」互相看见**，而引擎里的那份要等各自发布才更新 —— 本次 4 个区块组的
   任务在同一轮里跑，谁先谁后用它们各自的旧快照，**先发布的那份旧结果会盖住后发布的正确结果**；
2. **没有任何机制会去重读**：某个区块组被邻居发布覆盖后，它的外部失效标记（`externalSections`）只是躺着，
   而任务只在「该区块组有新的方块改动」时才排 —— 所以这份残留会**一直卡到玩家再编辑那附近**（这正好解释了
   以前的报告里「放个方块/重放光源就好了」）。

**这是 pre-existing 缺陷**：`tryRemoveNeighbor` / `processAdds` / 跨区发布这条路，PR #1（1.2.7）没有改过；
PR #1 修的是世界生成那条路的材质/光照基线，两者是同一类问题的两个位置。

## 试过但**没有**修好的两条（别再重复）

1. **`-Dlucistarlink.haloPublish=false`**：把 halo 发布整个关掉。gen 的残留**照旧**（小范围那组指纹一字不变，
   因为它本来就跟 halo 发布无关）→ 说明元凶不是「halo 被写回引擎」，而是**halo 这份陈旧副本被当成了传播基线**。
2. **每任务重读 halo 的光和材质**（`materializeReach` 去掉「已物化就跳过」，只对 halo 生效）：改完之后
   `sumAfter` **一格没变**（2345），gen 指纹只是从 `45b3fe94…` 变成 `2b9a8d8e…`（残留换了个形状）。
   原因：重读拿到的**引擎值本身还是旧的**（邻居区块组还没发布它的清除结果），所以只是把同一份旧数据又读了一遍。
   → 该改动**已回退**，没有留在代码里（它还有性能代价，且没有证明收益）。

## 下一步的修复方向（尚未实现）

要让多区块组的清除**收敛**，必须让区块组之间对「**世界里的方块**」达成一致，而不是互相读对方的旧光照：

- 触发点：跨边界的**光照减少**（`hasEmissionChange` 且新发光低于旧发光）+ `changesNearBorder`；
- 动作：给受影响的相邻区块组排一个**修复型整体重算**（`enqueueFullRelight`），并且这条路上**halo 的材质与光照
  都必须全量重读**（`populate(..., lazyHaloMaterials=false)`），否则重算会拿旧 halo 的发光值把光又点亮；
- 收敛性理由：整体重算是**从世界方块出发**的（发光/不透明度 + 从零传播），不依赖邻居那份可能过期的光照，
  所以两个区块组各自算出的重叠格结果必然一致 —— 这也是「重进一次就好了」的原因（重进走的就是这条路）；
- 代价与验证：只在「骑边界的清除」这一形状上触发（`structure_cube` 那类负载本来就会走整体重算）；
  必须按仓库标准证：交错 A/B ≥5 轮（`block_toggle_border` 首当其冲）+ `ls-refill-probe.sh` 的 gen 与 reload
  指纹逐位一致 + 既有的 `ls-border-edit.sh` / `ls-halo-probe.sh` 不回归。

## 给用户的临时办法（当前版本）

- 已经坏掉的地方：`/lucistarlink relight 256`（分区域跑），或者保存退出重进（重进会重算，但**只有在该区块
  保存时被标成「光照未正确」才会重算** —— 所以不保证每次都灵，`relight` 才可靠）。
- 避免触发：大范围 `fill` **按区块拆开做**（每个 16×16 分开），尤其是最后一步是 `fill air`（清除）的时候；
  或者清完之后**在附近随便放/拆一个方块**，把那个区域的任务重新排起来。
- `haloPublish=false` **不是**这个问题的解（实测无效）。

## 2026-09-20 追加：大神补了其中一条洞（已合并），但探针还判不出来

`lbw14514` 在同一个分支上又推了一条（`2ae33d0`，合并提交 `51f466a`）：**lazy 提取时把 halo 的 emission 清成 0**
（opacity 不动，理由写得很准：emission 是光源、保留的是上次提取时的值，而那时邻居那边可能还有发光方块；
全量重算会拿它当光源，在区域边界留一圈本该消失的光）。它补的是**全量重算**那条路的洞；
本文上面定位的**运行期增量**那条路（`tryRemoveNeighbor` 把邻居的旧光当独立光源）**没有被碰**，
计数器特征（`sumBefore=3840 → sumAfter=2345`）依旧成立。

**必须更正一处方法论**：`ls-refill-probe.sh` 的指纹**不能跨 run 比较** —— 同一个 jar 跑两次，
连「荧石亮着」那一步的**天光**都对不上（新生成区块的光照本身逐 run 波动，就是 `docs/HANDOVER.md`
的 Unresolved 3「worldgen 边界顺序」）。所以「拿一次修复前的 run 和一次修复后的 run 比指纹」这种对照
**无效**，本次 A/B 的结论因此作废（已记录，避免后人再踩）。可用的判定只有两类：

1. **同一个 run 内**的对照（空气状态 vs 重进后；重进的指纹每次都稳定等于全黑 `b93a0c83ce3b6325`，
   因为它走的是「从世界重算」），以及
2. 带**计数器**的同 run 证据（`sumAfter` 是否为 0）。

要让这条缺陷真正判得出来，探针需要先做到「新生成区块的确定性」：固定生成顺序（例如先把世界完整生成好、
再开始场景），或者完全不依赖世界生成（在一个手工搭好的场地里做 fill 循环）。

## 2026-09-20 再追加：探针已经可复现，判定「这条修复没有消除残留」

探针加了 `prep` 阶段（先把世界**完整生成好**并保存，`gen`/`reload` 只在已生成的世界里编辑和读取）。
同世界、同场景下指纹全部复现（荧石态 `6b6cbf1070003325` 两次一致；重进态稳定 = 全黑规范值）。有效的 A/B：

| 构建 | 空气那一步（内存里） | 重进后 |
| --- | --- | --- |
| 合并后（含 `2ae33d0`） | `45b3fe947d9ab5cd` ✗ | `b93a0c83ce3b6325` ✓ |
| 未修复（1.2.7 发布件） | `3206f1df4c73167c` ✗ | `b93a0c83ce3b6325` ✓ |

**两版都没回到全黑**：这条修复**改变了残留的形状**（说明它确实作用于其中的一部分），但没有消除它。
和上面的定位一致 —— 它补的是**全量重算**那条路，本文定位的是**运行期增量**那条路。

**为什么探针里重进是干净的，而用户的世界会坏**：探针最后那次存盘时，引擎里还有挂着的任务，
`shouldRelightOnLoad` 于是把 10~11 个区块判成「光照未正确」（遥测计数 `save forced light-incorrect: pending 10/11`），
重进时这些区块被重算 → 干净。**用户那边是引擎空闲时保存的**：区块自称「光照已完成」，重进直接读盘里那份
残留 → 残留光照出现在客户端。这就是两者差别，不是随机。

## 正确的修法（尚未实现，含一条必须遵守的代价约束）

想让跨区块组的**清除**收敛，必须让参与的那个区块组在**同一张图像里**看到**邻居的待处理改动**，
而不是只看到邻居那份旧光照：

- 触发点：批次里出现**光照下降**（新发光 < 旧发光）且 `changesNearBorder`；
- 做法：把**相邻区块组在该 halo 范围内的待处理记录也取进这次计算**（只读、不消费，它们仍由各自的任务处理），
  在自己的图像里一并应用 → 图像与**世界方块**一致 → 清除波不再把邻居的旧光当独立光源 → 发布出去的 halo 就是对的；
  两个区块组各自算出的重叠格必然一致，于是收敛。
- **不要**用「跨边界清除就整片重算」这种粗暴触发：`block_toggle_border` 负载每轮都在边界上放/拆方块，
  每轮多一次整体重算会把我们最大的优势档直接打掉（那个档现在是 0.8 ms 级，整体重算是毫秒级）。
  这也是本条必须按上面「取邻居待处理改动」来做、而不是按「整片重算」做的原因。
- 验收：`ls-refill-probe.sh prep/gen/reload` 三段跑完，空气那一步必须等于全黑规范值 `b93a0c83ce3b6325`
  （现在两版都不是）；外加 `block_toggle_border` 的交错 A/B ≥5 轮确认没有把优势档打掉。
