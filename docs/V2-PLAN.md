本文是**执行计划**，不是设计书。设计（为什么这么改、引擎记账的每个坑、三个核心概念、生命周期图）见

## 1. 为什么做 V2 —— 依据全部是实测，不是推断

### 1.1 事情是这样的

`sky_hole`（天空/高处的小改动）这一档我们比 ScalableLux 慢 **2.0 倍**（0.708 vs 0.355 ms，同场交错 10+10，U=100/100，p<0.0001）；
另外三档我们赢或接近（拆建 2.05×、结构 1.77×、密集慢 21%）。这一点在 v1 发布前**已经定性**：

| 已测事实 | 数据 | 含义 |
|---|---|---|
| 我们的计算**不在关键路径**上 | 关掉光环：运行期作业 17.3 → 6.8 ms、物化 12.6 → 2.8 ms，pass 时间**纹丝不动**（p=0.74） | 优化计算救不了这一档 |
| 交付侧的 14 个杠杆**全部无效或更差** | 合并窗口 ×3、通知扇出、发布分道、内联阈值、直装（含 n=25）、piggyback、promptDispatch（更差）、同步通道三件套（p=0.91） | 不是漏了开关 |
| pass 的构成 | apply ~0.12 + **一条固有异步链**（申请 → 线程跳 → 引擎吸收 → future 完成）≈ 0.75~0.85 ms | 差距在链上 |
| ScalableLux 的 0.31~0.43 ms | 它在 `setBlock` 里**同步**算完，不排队、不交付、没有待处理队列 | 它的下限天然比我们低 |

**结论**：那 ~0.4 ms 不在任何我们能单独替换的零件里，而在"把 section 交回引擎"这条链的**存在本身**。
要消除它，只能让**存储归我们所有** —— 也就是 V2 的 storage 模式。这是唯一路径，也是唯一可能**反超**（而非追平）的路径。

### 1.2 预期收益的诚实边界

- 上限：`sky_hole` 从 2.0× 落后 → **约 1.0~1.1×**（即持平）。**不承诺反超**。
- 副产品（同等重要）：halo 发布、外部刷新、漂移重跑这三条**为"我们持有独立映像"而存在的跨区机制**在 storage 模式下不再需要，
  代码**净减少**；这也是 ARCH-V2 里"删繁就简"的本意。
- 三档重负载不得回归（它们是当前对外的优势表述）。

## 2. 目标与验收（可测、可回退、不放宽正确性）

### 2.1 性能验收（已按 v1 期间修正过的口径，不是旧文档里的绝对线）

> **注意：ARCH-V2 §6 里写的"`sky_hole` min ≤ 3.0 ms"是已废弃的绝对线**（那个口径把"何时交活"混进来了）。
> 现行口径：**`minPassNanos` 中位数、≥5 轮、同场逐轮交错、附精确双尾 Mann-Whitney**，且**比值需独立复现一次**。

| 项 | 门槛 |
|---|---|
| 主目标 | `sky_hole`：我们 ÷ SL 的比值 **≤ 1.05**（同场交错 ≥5 轮，p<0.05，独立复现一次） |
| 护栏 | 另外三档各自的比值**不比 1.0.0 差 5% 以上**（同一协议） |
| 量具 | 一律 `prepareRing=3` + `quiesceSettleMs=1000`（缺这两个参数的组**不可比**，见 TASK-PERF-SKY §7.8） |

### 2.2 工程验收（与性能同等重要）

- `region` 模式**仍可用**且**仍是默认**，直到阶段 5 全部门槛通过；
- storage 模式下**删掉**至少两条跨区机制的分支（halo 发布 / 外部刷新 / 漂移重跑三者中的两条），代码净减少；
- 一行配置可切：`lightEngineMode = region | storage`（系统属性 `-Dlucistarlink.lightEngineMode=` 同样支持）。

### 2.3 正确性门槛（**与 1.0.0 完全一致，不允许为性能放宽任何一条**）

1. 差分套件 **21 项全绿**（`./gradlew test`）；
2. **相邻成对探针 0 偏差**：同一世界快照、同一次运行时边界编辑，无流体气层带（y=90~112）与原版**逐位一致**
   —— 1.0.0 的记录是 5 个标签全一致，这是基线；
3. **存档往返**：`gen` 与 `reload` 的指纹一致；
4. **客户端同步用例**：边界放光 2 秒内在已连接客户端两侧可见，无需重连
   （装置：`mc-smoketest/clientcase.sh` + 定时 datapack + 全分辨率 F2 帧逐像素比较）；
5. 任何"靠关掉正确性换来的数字"（`haloPublish=false`、`runtimeHaloChunks=0`、跳过复查）**一律不算数**。

### 2.4 回退

- 阶段 0–4 期间：`lightEngineMode=region` 即为 1.0.0 行为；
- 阶段 5 之后：保留一行开关切回 region 模式 + `dist/lucistarlink-1.21.1-1.0.0.jar` 作为成品回退件。

## 3. 实施阶段（对齐 ARCH-V2 §3，每阶段独立交付、独立验收、独立回退）

### 阶段 0：抽象存储后端（纯重构，行为不变）—— 约 1 天
**做什么**：引入 `SectionStore` 接口（读一个 section / 写一个 section / 通知一个 section 变化 / 标记脏），
region 模式实现为"写回引擎"的现有路径（**行为零变化**）；新增配置项 `lightEngineMode`（只解析、只打日志，不生效）；
新增 telemetry 计数器占位（`storage.write.sections`、`storage.notify.sections`、`storage.mode`）。
**改哪些文件**：新增 `light/store/SectionStore.java` + `RegionSectionStore.java`；`LuxConfig`（新键）；`LuciStarlink`（启动日志）。
**验收**：21 项测试绿；四档交错 A/B（我们 vs 我们，`ab-prop.sh` 同参数两组）**无差异**；探针 0 偏差。

### 阶段 1：引擎存储后端（读 + 记账，先不写）—— 约 2–3 天
**做什么**：storage 模式下让**读取**直接来自引擎存储（不再维护独立映像的读路径）；把"引擎记账"按 ARCH-V2 §2.3 逐项对齐
（`updating`/`visible` 两层、`clearCache()`、`queuedSections` 遮蔽、`updateSectionStatus` 的邻居登记）；
**先只读不写**，用一个"影子对比"计数器记录"如果写会写哪些 section"。
**验收**：影子模式下 storage 与 region 的读数**逐 section 一致**（新增入口 `/lucistarlink dumpplane` 对比）；测试绿；性能不回归。

### 阶段 2：storage 模式的提交路径（**主要收益在这一步**）—— 约 3–4 天
**做什么**：写入走 `SectionStore`（**原地覆盖 `DataLayer`，绝不换对象**）+ **每个真正变化的 section 通知一次**
（不做 27 邻位扇出 —— ScalableLux 就是这么做的，而我们已有客户端用例可证伪）；运行期路径先接，worldgen 后接。
**验收**：`sky_hole` 交错表（vs SL ≥5 轮，附 p）**必须出现可测改善**；四档不回归；探针 0 偏差；客户端用例通过；
**并且**：链必须真的消失 —— 见 §5 熔断条件第 1 条。

### 阶段 3：删繁就简（storage 模式成为默认之后）—— 约 2 天
**做什么**：storage 模式下停用并**删除**halo 发布、外部刷新、漂移重跑三条机制的分支（region 模式保留其实现）；
同时删除 `experimentalBoundaryDeltas` + `BorderDeltaSupport`（1.1 已计划清理的死原型）。
**验收**：代码净减少（给出前后行数）；测试绿；探针 0 偏差；三档不回归。

### 阶段 4：客户端（新架构的额外收益）—— 单独评估，**不在本计划承诺范围**
ARCH-V2 认为 storage 模式让客户端接管更容易；但客户端接管是**新功能**，需独立立项与验收。

### 阶段 5：切换默认值 —— 约 1–2 天
**做什么**：把 `lightEngineMode` 默认改为 `storage`（**单个提交**，提交信息带 §2.1 的完整数字），
保留一行开关回退；重建发布件（`dist/`，md5 重新记录）。
**前置（缺一不可）**：四路/三路表（≥5 轮、交错、附 p）+ 客户端用例 + 存档往返 + **30 分钟长跑内存遥测** + 探针 0 偏差。

## 4. 风险与对策（按严重度）

| 风险 | 后果 | 对策 |
|---|---|---|
| **光值与原版分歧** | 玩家看到错的光 | 每阶段探针（相邻对 + 气层带）；差分套件；**出现分歧立即停**，不允许"先合并再查" |
| **客户端出现黑缝** | 边界视觉 bug | 每 section 通知一次（SL 先例）+ 客户端用例必须过；不许用"多扇出"掩盖问题 |
| **存档丢光** | 玩家数据损坏 | 沿用 1.0.0 的精确模式 `isLightCorrect` 语义 + 存档往返用例 |
| **并发写入竞态** | 随机、难复现的坏数据 | **所有写入只允许在光照线程**（1.0.0 的 `installSection` 已确立此约束）；`SectionStore` 在非光照线程调用时直接抛错（fail fast） |
| **性能反退化** | 白干 | 每阶段跑交错 A/B；三档护栏（§2.1） |
| **实现漂移（V2 变成"又一套机制"）** | 复杂度回升 | §6 的"不做清单" + 阶段 3 的删除是硬要求 |
| **收益不达预期** | 投入打水漂 | §5 熔断条件，**阶段 1 末即可判定** |

## 5. 熔断条件（什么情况下**放弃** V2）

1. **阶段 1 结束后**，若 `sky_hole` 的改善 **< 15%**（说明那条链并没有因为存储易主而消失）→ **立即停止 V2**，
   转回"接受 2×、把对外表述固定"的路线；这条最重要，因为它是整个 V2 收益假设的直接检验。
2. 任何阶段出现探针偏差，且 **3 个工作日内无法定位**；
3. 阶段 2 之后三档出现 **> 5%** 的回归且修不回来；
4. 出现"必须放宽 §2.3 中任何一条正确性门槛才能继续"的情况 → **直接停**。

---

## 6. 明确不做的事（防止范围蔓延）

- 不做客户端光照接管（那是阶段 4，独立立项）；
- 不动 `region` 模式的默认行为，也不删除它的实现；
- 不改变存档格式；
- 不引入新依赖；不新增 mixin 目标类（`LightEngineAccessor` / `LayerLightSectionStorageAccessor` 已存在）；
- 不为任何数字牺牲 §2.3 的正确性门槛；
- 不在同一次改动里同时动"存储易主"和"调度策略"（两者必须能分别回退）。

## 9. 自检遗留项（1.1 清理清单，均已核实、均非现存 bug）

1.0.0 发布前做了一轮全源码自检（512 文件 / 8484 行的范围内逐项核对）。**四个真 bug 已修进 1.0.0**；
下面这些是**防御性或整洁性**问题，故意没有在发布前动它们（任何代码改动都会让刚发布的 1.0.0 指纹失效）：

| 项 | 位置 | 为什么要清 | 风险 |
|---|---|---|---|
| 发布/通知队列无上限 | `ThreadedLevelLightEngineMixin` 的 `pendingLightTasks` / `pendingRuntimeTasks` / `pendingLightNotifications`(+keys) / `pendingPublishes` / `publishCompletions` | 上游是每 tick 的作业结果与最多 27 倍的扇出，而只有光照线程消费；光照线程长阻塞时它们只增不减（其它缓存都已有字节/条数上限） | 中（需先有"光照线程卡住"的复现路径） |
| `RuntimeBulkScope.regionChangeCounts` 无上限 | `LuxEngineController` | 一次巨大 `/fill` 会为每个触及区域留一条；有 30 秒空闲回收兜底，但打开期间无约束 | 低 |
| `currentLightSource` 是单个 volatile、被当作"每作业上下文" | `LuxPublishEngine` | 多维度并发作业会互相覆盖取源；后果只是"跳过相同段"的判断可能跨维度误判（少发布一段，不会算错光） | 低（设计味道） |
| `LuxScheduler` 同一属性读两次且把 1~3 静默抬到 4 | `light/runtime/LuxScheduler.java` | 配置意图被无声改写 | 低 |
| 孤儿 javadoc（注释挂到了下一个声明） | `LuxRelighter:73-83`、`RegionLightData:99-103`、`LuxRuntimeManager:165-169` | 读者会看错归属 | 极低 |
| `haloChunks` / `runtimeHaloChunks` 命名易混 | `LuxConfig` | 前者是世界生成映像的光环，后者是运行期作业的光环；注释已写清，名字没跟上 | 极低 |
| 被否决的 delta 原型 | `BorderDeltaSupport` + `experimentalBoundaryDeltas`（+ 测试与 5 处文档引用） | 唯一"任何配置都开启不了、但连着 sky/block 引擎"的死代码；阶段 3 一并删除 | 中（删它要动两个光照引擎） |
| 四个被否决的实验开关 | `piggybackPublish` / `promptRuntimePublish` / `syncRuntimeDrain` / `directSectionInstall` | 都已被实测否定、默认全关；保留是为了能复现实验，应在文档里标明"实验用、勿开" | 低 |
| 基准/诊断代码在主源集 | `test/LuxBenchmarkSupport`、`LuxClientLoadDiagnostics`、`LuxServerBenchmark` | dev 工具混进正式 mod（有 `lucistarlink.benchmark` + `debug` 双开关兜住，实际不会跑） | 极低 |
