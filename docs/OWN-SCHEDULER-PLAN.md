## 1. 为什么要做（一句话）

玩家口径已经四档全赢；**唯一输的是引擎口径的 `block_toggle_border`**（2.0 ≈ 4.3–5.4 ms，1.x 3.4 ms 中位 / 1.26–1.9 ms 好轮）。归因证明差距**不是算力**：我们每 pass 实际只干 25–62 µs 的传播，其余全是"完成信号"的延迟——1.x 的同步安装通道让"引擎报告完成"≈"调用返回"，而 SL 的并发队列让完成天然是一个更晚的事件。

## 2. 为什么必须是"换层"而不是"补丁"（九次实验的结论）

| # | 层次 | 结果 |
|---|---|---|
| 1–6 | 队列内部 / 调度判据 / 完成路径钩子 | 无效或更差 |
| 7 | 完成请求时排空 | 无效（计数器：484 次排空取到 0 个位置 ⇒ 队列已空） |
| 8 | 每 tick 服务器线程排空（正确性通过） | 更差 6.15 vs 4.86 |
| 9 | 绕过队列（抑制调度 + 完成请求时执行） | **服务器挂死**（`tasks=1 dirty=1` 永不排空） |

第 9 次给出根因：**SL 的并发队列同时承担"算光"和"保证总有人来排空"两个职责**。要它的前半、关掉后半，就破坏活性。所以不能挂接，只能替换。

## 3. 架构设计

**保留（不重写光照算法）**：`SkyStarLightEngine` / `BlockStarLightEngine` 的增量传播与 nibble 数组读写。

**换掉（自研）**：
1. `EditScheduler`——编辑入口的双通道：
   * **同步通道**：小改动（阈值可配）且区块已就绪（status ≥ LIGHT、已加载、主线程）→ 就地传播 + 就地安装 + **本地结掉完成信号**；
   * **异步通道**：批量改动、世界生成、跨区块边界 → 走现有队列（保留其活性保证）。
2. `CompletionLedger`——完成信号的本地结算：一次编辑的 future 在它的工作完成时立即就绪，不再经过"光照线程被调度"这一跳。
3. **硬排空点（活性保证）**：任何被同步通道推迟的工作都必须在**必有的一次调用**上排空——挂在服务器 tick 的硬钩子（`ServerLevel.tick` 级，而不是第 9 次那样挂在可能不被调用的 `tryScheduleUpdate` 上）；同时保留一个 tick 计数上限（超时释放给异步通道）。

**关键不变量（与已关闭的 `own-engine` v1 的本质区别）**：
* 光照真相**仍是引擎自己的 nibble 数组**，不引入区域图像 ⇒ **没有"材料交付"成本**（own-engine v1 正是死在那 48 µs/编辑的材料装配上）；
* 同步通道只覆盖"小改动 + 已就绪区块"；其余一律回到异步通道。

## 8. S1 进展与两个已知坑（2026-09-22 夜）

**已实现**（`-Dscalablelux.ownScheduler=true`，默认关）：`EditScheduler` 状态机（`markPending` / `drainOnDemand` / `onServerTick`）；`StarLightInterface.lucis$drainInline()`（**整次排空只取一次引擎实例**）；`schedulePropagation0` 在持有期直接返回；`syncFuture` 在完成请求时排空；`ServerLevelOwnSchedulerMixin` 挂在 `ServerLevel.tick`（保证每 tick 都到，第 9 次教训）。

**坑 1（已修，证据是线程转储）**：首次实现挂死在 `MinecraftServer.prepareLevels → waitUntilNextTick → waitForTasks`——**启动准备阶段根本不 tick**，而排空点挂在 `ServerLevel.tick` 上，被持有的 47 个任务永远没人排空。修法：`gameTime <= 0` 时不允许持有（同步通道只服务运行期编辑，准备期全部交回异步调度）。

**坑 2（已修）**：标记最初挂在 `ThreadedLevelLightEngineVanillaInterface.checkBlock` 上，而**实测编辑不经过它**（探针长期显示 `checkBlock=0`）——真正的收口是 `StarLightInterface.blockChange`。修好后 `ENGAGED` 出现、通道生效。

**还挂着（下一步要查）**：修好上面两处后，`structure_cube` + 指纹的一轮里 prepare 完成、测量 pass 也完成了（`minPass=3.73 ms`，好于基线 4.3–5.4 但**仍高于熔断线 1.5 ms**），随后整轮挂死在指纹/收尾阶段（`rc=124`）。下一件事：在挂住时抓线程转储，定位是"指纹 settle 等不到引擎空闲"还是"收尾/卸载路径"。

## 9. S1 结论：熔断触发，代码已撤（2026-09-22 夜）

**S1 实现了、测了、撤了。** 通道确实生效并把数字往正确方向推了（`minPass` 从 4.3–5.4 降到 3.73 ms），但它**三次挂死服务器**，两次线程转储把原因钉死：

1. **启动准备阶段**（已修但只是补丁）：`prepareLevels → waitUntilNextTick → waitForTasks` —— 该阶段不 tick，挂在 tick 上的排空点永远不会触发。修法是 `gameTime ≤ 0` 不持有。
2. **阻塞式读区块（设计性冲突，无法用补丁解决）**：指纹阶段读一个方块 → 服务器线程在 `ServerChunkCache.getChunk → managedBlock → waitForTasks` 上**永久 park**，而它等的正是被通道持有的光照 → 线程 park 住 ⇒ tick 不推进 ⇒ tick 驱动的释放阀永不触发：**真正的互锁**。
3. 在 `loadInChunk` / `forceLoadInChunk` / `lightChunk` 三个入口补排空点后，**同一个挂死原样复现**。

**架构结论（这才是这次工作的价值）**：**"延迟光照工作"只有在"任何地方都不会阻塞等引擎 settle"时才安全**——而 Minecraft 里任何对未加载区块的 `getBlockState` 都正是这种等待。**1.x 能做同步安装，是因为它从不延迟**（调用即算完）。要复刻它，就必须**在每次编辑调用内当场算完**，也就是当初 own-engine 被关闭的那个成本问题（约 48 µs/编辑 vs ScalableLux 约 34 µs）。

**因此本项目的结论**：这条路要成立，前提是"每改动当场算"的成本能被压到与 SL 相当——这不是调度层能解决的，而是光照算法与存储层的题目。`EditScheduler` 保留为 S0 骨架（入口与不变量已命名，未接线，默认关），本项目暂停在这一步。

**至此该格累计 11 次尝试**：1–6 队列内部钩子（无效/更差）、7 完成请求排空（无效）、8 每 tick 排空（更差，正确性通过）、9 抑制调度（挂死）、10 S1 v1（通道生效、3.73 ms，仍不达标）、11 S1 v2（挂死 ×2，互锁定性）。

**环境坑（每次都要做）**：挂死的 JVM 会占住 25565，导致后续运行以 `BindException` 静默失败（日志里只有一行 WARN，很容易被当成"rc=0 成功"）。**每次运行前必须：杀全部 java → 确认 `netstat` 无 25565 → 再跑**；跑完检查日志里没有 `BindException` 才算有效。

## 10. 第 12 次尝试（收窄到"只扣编辑任务"）——也失败，且给出了最终定性

第 11 次挂死的原因是"全局抑制调度"把**加载期/世界生成**的光照也扣住了，所以第 12 次把持有范围**收窄到只扣"编辑产生的区块键"**（`EditScheduler.markEdit` 记录编辑键，调度器只跳过这些键，其余照常流向光照线程；排空时先执行被扣的编辑任务）。

**结果**：仍然挂死，而且换到了**新的两个阶段**：

| 挂点 | 阶段 | 现象 |
|---|---|---|
| #1 | tick 之前（`prepareLevels`） | 该阶段不 tick，挂在 tick 上的释放阀不触发（第 10 次已修，但只是补丁） |
| #2/#3 | 指纹阶段 | `getChunk → managedBlock → waitForTasks` 阻塞等区块，而该区块的光照被扣住 ⇒ 自我依赖互锁 |
| #4/#5 | **prepare 阶段 + 关服阶段** | prepare 240 s 跑不完；`Stopping server → waitUntilNextTick → waitForTasks` 卡住 |

**最终定性（这是本项目的真正产出）**：**四次挂死分别落在四个不同阶段**——每收窄一次持有范围，挂点就搬到下一个阶段。这说明它不是"范围没调对"，而是：

> **在这个底座上，"等光照 settle"的等待者存在于每一个阶段**（启动准备、世界生成、区块加载、指纹/读方块、关服保存）。因此**任何"把光照推迟"的设计都必然与其中某个阶段互锁**。

**1.x 之所以能"当场安装"，根本原因是它拥有自己的光照数据**：没有"待处理"这个状态，也就没有可被等待的延迟。要复刻它，只能把数据所有权一起拿过来（= own-engine 方向，成本已关闭）；而在不拿所有权的前提下（即"在 SL 上优化"），这一格**在原理上不可达**——12 次尝试、4 份线程转储、1 次成本分解，证据一致。
