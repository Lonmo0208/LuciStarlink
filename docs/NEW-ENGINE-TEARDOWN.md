## 0. 新引擎必须同时满足的硬约束（前序工作换来的）

1. **当场算完**（否则任何等待者都会与延迟互锁——四次挂死分别落在四个阶段证明了这点）；
2. **拥有自己的光照真相**（否则"待处理"状态必然存在，1 无法成立）；
3. **但发布面必须与别人一致**：原版读的就是 chunk section 里的 nibble 数组（客户端发包、存档、其它模组），所以安装必须写回同一批数组（1.x 也是这么做的）；
4. **正确性契约不可退**：安装同时写 updating + visible（1.1.5 的教训）、跨区减光不截断（1.2.9）、重启不截断、worldgen 自然光与原版一致（1.2.7）；
5. **活性**：任何"持有/排队"都必须有**保证会发生**的排空点；本次证明了"保证"很难凑齐 ⇒ 新引擎的设计目标应是**不持有**。

## 1. 层级拆解

| # | 层 | 2.0（SL 底座 + 我们） | 1.x（Lucis 系 + 我们） | 谁强 / 新架构取谁 |
|---|---|---|---|---|
| L1 | **光照真相** | 原版 `DataLayer`（section 内 nibble），引擎只读写 | **自己的区域图像**（region images）为算，结果发布到原版数组 | 1.x 的**算用自有、存用原版**是唯一能"当场算完"的形态 ⇒ **取 1.x 形态** |
| L2 | **编辑入口** | `blockChange` → 队列（`ChunkTasks`+票据），完成在后 | 同步发布通道（`directSectionInstall`+`syncRuntimeDrain`），**调用内安装** | **取 1.x**（必须当场） |
| L3 | **传播算法** | 逐格增量 BFS（每改动 0.3–0.65 µs；每 pass 全部传播 23–30 µs） | 区域重算 + 均匀光源跳过 + 精确双队列天空光修复 | **两者都取**：小改动走增量（SL 便宜），批量改动走区域摊销（1.x 便宜）——**这是"批量通道"的设计依据** |
| L4 | **安装/发布** | 脏 section 只发一次（我们加的"内容未变不发通知"） | 脏 section 发布 + halo/跨区发布 | **取 1.x 的直装语义 + 我们"内容未变不发"的过滤** |
| L5 | **客户端同步** | 每层一个 BitSet、每 chunk 每 tick 至多一包、空层零负载（实测已最小） | 1.2.5 的 −51% 老问题已在新底座上不存在 | **取 2.0**（现状即最优，别再优化它） |
| L6 | **调度与活性** | 光照线程 + 队列（底座）= 活性保证，但带来完成延迟 | 自有 worker + 区域作业；同步通道绕开队列 | **新架构：不排队 ⇒ 不需要"光照线程"这个活性保证**；批量与世界生成仍用 worker 池 |
| L7 | **区块生命周期** | 票据 / `ChunkTasks` / `onComplete` 把"区块别卸载"和"完成"绑在一起 | 区域 init/adoption-backed 初始化 | 新架构需要**显式的区块引用计数**（谁在用、何时可卸载），这是 L1 自持的代价之一 |
| L8 | **存档/重启** | 原版两钩子（append unsaved lighting / force light incorrect before save），审计为等价或更强 | 1.1.5 重启修复、1.2.9 跨区减光修复 | **取两家并集**（审计结论 + 我们两个真实缺陷的修复） |
| L9 | **worldgen** | `WorldGenRegionMixin` 未点亮前返回 0；异步队列 | PR#1 worldgen 自然光修复；已知 80 格缺陷（我们的 bug） | **取 2.0 的路径 + 1.x 的修复经验**；80 格缺陷必须在新引擎里不复现 |
| L10 | **配置/兼容/可观测** | 配置面 + Sable 门控 + `/lucistarlink stats\|light\|relight` + `SLTELEM`（我们加的） | 25 键配置 + Sable + 内存遥测 | **全取我们这一层（两边都是我们写的）** |
| L11 | **测量基础设施** | 按-pass 探针、箱内判据、契约协议（本次建成） | 同 | **全取**，并作为新引擎的验收工具 |

## 2. 已知成本地板（新引擎的设计预算）

| 量 | 实测 | 出处 |
|---|---|---|
| 单格增量传播 | **0.3–0.65 µs/改动** | 本分支 M2-2 |
| 一个区域/一批的作业（含取还） | **250–600 µs/批** | 1.x runtime 队列 |
| 1.x 一次 pass 的区域口径 | **1.26–3.4 ms**（拆/放档） | 6 轮校准 |
| **材料交付（own-engine v1 的死因）** | 逐格 536–2808 µs → 调色板 API **375–1071 µs（≈45 ns/格）**；乐观组合 ≈48 µs/编辑 vs SL ≈34 µs | `OWN-ENGINE.md` |
| own-engine v1 核心（原地传播，逐格验证正确） | **13.4 µs/编辑** | `OWN-ENGINE.md` |
| 2.0 每 pass "能摸到"的总量（拆/放档） | 入队 30–123 µs + 传播 23–30 µs + apply ~172 µs | 本次成本分解 |
| 2.0 完成延迟（同一格剩下的） | **≈4.3 ms** | 本次 |

**预算结论**：新引擎的每次编辑预算 ≈ 1.x 的 1.26 ms / 95 改动 ≈ **13 µs/编辑**；其中**材料/安装不能超过几微秒**——这正是 v1 撞墙的地方，所以 L1 的自有真相必须**按"算的时候就在自己的格子里"设计**（不要再有"从原版数组反抽材料"这一步）。

## 3. 由此确定的新引擎形态（初稿）

```
编辑(服务器线程)
  └─ 自有光场（每 section 一份 nibble，与 ID 映射表）
       ├─ 单格增量传播（SL 的算法，0.3–0.65 µs）
       ├─ 批量：同一 section 内 ≥K 个改动 → 一次分区重算（1.x 的摊销）
       └─ 安装：直接写回该 section 的原版数组（updating+visible）+ 标脏
  └─ 通知：脏 section → 合并 → 每 chunk 每 tick 一包（L5 现状）
  └─ 完成：本地（无队列、无 future）
批量/世界生成/区块加载：worker 池（保留活性），但它们的完成与"编辑完成"解耦
```

**与 own-engine v1 的关键差别**（v1 死于材料交付）：
* v1：编辑 → 需要材料 → **从原版数组反抽 4096 格** → 太贵；
* 新：编辑 → **自己的光场就是材料**（自持 nibble）→ 只碰受影响的格子 → 无"抽取"这一步。
⇒ **自持 nibble（不是区域图像）** 是 v1 与本次设计的分水岭，也是这次可能成功的原因。

## 7. 里程碑实况（2026-09-22 夜）

**R1 ✅ PASS**：`OwnLightField` 整段往返 `cells=4096 mismatches=0 roundTripNanos=1158`（逐格、含 updating+visible、含邻格未被污染）。

**R2 ✅ 机制成立 / ❌ 单独不达标**：`-Dscalablelux.ownEdit=true` 在 `blockChange` 内直接调 `blocksChangedInChunk`（不经队列）。

**R3 ✅ 合并生效**：改动先攒进"该区块的待办集合"，在**换区块 / 集合满 256 / `syncFuture`（完成请求）/ `hasUpdates()`（每 tick 必到的引擎查询）**四个点刷新，一次调用处理整批。
* **~20 次调用处理 4100 个改动**（合并比 ≈200×），`ownEditBatched` 逐 pass 可见；
* 指缴一致、四阶段无挂死（关探针的 A/B 六轮全绿）；
* **建筑档 minPass 4.32 ms**（基线 6.14、1.x 6.09）→ **该档已胜**；
* 拆/放档 4.26 vs 基线 4.41 → 略胜，**未达 1.5 ms**；
* 与队列相比少了"完成信号"这一整块（我们从不入队，`getChunkSyncFuture` 无任务时返回已完成的 future ✓ 已确认）。

**一个底座侧的真实故障（待处理）**：`border + 探针开 + ownEdit 开` 的一轮里，区块生成期抛出
`IllegalMonitorStateException @ StampedLock.unlockRead` ← `ConcurrentLightQueue.getOrCreateChunkTasks` ← `queueChunkLighting` ← `lightChunk` ← `ChunkStatusTasks.light`。
**是底座队列自己的锁协议**，关探针的同 jar A/B（六轮）与结构档开探针都正常 ⇒ 我们的额外服务器线程引擎工作很可能只是"踩醒"了它。
**对策（下一步）**：收紧就地通行的资格——只在**该区块与其 3×3 邻域都已加载且 ≥LIGHT / light-correct**（即 SL 自己 `canUseChunk` 的语义）时才走就地路径，其余一律交回队列。这同时满足"只有完全就绪才当场算"的设计原则。

**拆/放档剩余 ~4 ms 的归因方向（下一步）**：已知它不是入队、不是完成信号、不是批量开销（三者都已排除）；接下来量 `blocksChangedInChunk` 内部的 **setupCaches / 传播 / updateVisible** 三段，判断是"边界传播算法本身贵"还是"可见层发布贵"。

## 8. 归因结果 + 一个底座崩溃级 bug 被修掉（2026-09-22 深夜）

**先修了一个底座的真 bug（崩溃级）。** 拆/放档 + 探针的每一轮都抛
`IllegalMonitorStateException @ StampedLock.unlockRead ← ConcurrentLightQueue.getOrCreateChunkTasks ← queueChunkLighting ← lightChunk ← ChunkStatusTasks.light`，
随后 "Exception generating new chunk" → 服务器停止。**对照实验证明与 R2/R3 无关**（`ownEdit` 关掉、同 jar、同参数，异常一模一样）。根因在底座队列：

```java
long stamp = this.tasksLock.tryOptimisticRead();   // 乐观读：不是持有凭证
...
if (tryReadAgain) {                                 // 校验失败进入此分支
    tasks = this.chunkTasks.get(key);
    if (tasks != null) { this.tasksLock.unlockRead(stamp); return tasks; }   // ← 用乐观 stamp 解锁
    writeStamp = this.tasksLock.tryConvertToWriteLock(stamp);                // ← 同样需要真实读锁 stamp
```
**该分支从未真正获取读锁**，却调用 `unlockRead`/`tryConvertToWriteLock` ⇒ 竞态触发崩溃。修法：在该分支开头补上 `stamp = this.tasksLock.readLock();`。
**验证：拆/放档 + 探针连续三轮 `rc=0`、零异常**（修复前每轮必挂）。生产服务器同样可能撞上这个竞态，值得单独记录/上报上游。

**归因：拆/放档的 ~4 ms 是真实传播工作，队列只是把它藏进了"等待"。** 给 `StarLightEngine.blocksChangedInChunk` 加了两段常开计时（`setupNanos` / `workNanos`，成本 ~50 ns/次，不依赖探针开关）：

| 拆/放档，每 pass（**异步路径**，`ownEditInline=0`） | 实测 |
|---|---|
| setupCaches（建缓存） | **0.11–0.17 ms**（≈5 µs/次，可忽略） |
| **传播 + 发布（work）** | **4.2–11.9 ms** ← 真正的成本 |
| 入队 / 锁 / 完成信号 | 已排除 |

⇒ **同一批改动的传播成本在两条路径上都存在**（4–5 ms），异步路径把它记在 `wait`（4.4 ms），我们的就地路径把它记在 `apply`（4.8 ms）——所以两者读数接近不是巧合，而是**同一笔工作**。1.x 做同样的活只要 **1.26–3.4 ms** ⇒ **剩下的差距是算法：跨区块边界的传播成本**，不是调度/完成/批量（这三样都已解决）。

**下一步（算法侧）**：把 `workNanos` 再拆成"传播（`propagateBlockChanges`）"与"可见层发布（`updateVisible`）"，判断 1.x 的优势来自哪一侧（它的做法：区域重算摊销 + 只发布变脏的分区）。

## 9. 算法靶子收窄到单个方法（2026-09-22 深夜）

在共享入口 `blocksChangedInChunk` 里按引擎类型分桶计时后，拆/放档每 pass 的成本分布是：

| 段 | 实测 |
|---|---|
| `setupCaches`（建缓存） | 0.12–0.17 ms |
| **天空光引擎** | **0.18–0.26 ms** |
| **方块光引擎** | **4.19–5.95 ms** ← 全部成本 |
| `updateVisible`（可见层发布） | 0.08–0.10 ms |

同一批改动（95 次编辑、约 106 次 nibble 写入、17–19 次调用），**天空光比方块光便宜 20 倍**。这一档放的是光源（glowstone 类），方块光要从区块边界向外扩散 ⇒ 成本集中在**方块光引擎每次调用的固定开销**（约 250 µs/次，每次只写约 6 个格子）。

**R4 的第一个算法任务**：进 `BlockStarLightEngine.propagateBlockChanges` 内部再分段（种子写入 / 增长-衰减队列处理 / 边缘检查 / 每区块初始化），找出那 250 µs 的构成并把它摊销掉。这也正是 1.x（同档 1.26–3.4 ms）领先的来源。

## 10. R4-1 命中：四档引擎口径全赢（2026-09-22 深夜）

**分段结果把靶子指到一个语句上**（拆/放档，每 pass）：种子写入循环 `blkCheckNanos` **12–19 µs**，而 **`performLightDecrease` 3.95–7.74 ms**——占该格 98%。它每次调用（约 18 次/pass）花 220–430 µs，处理的是**引擎自己的全局衰减队列**（用"本次调用前的队列长度"为界）⇒ 每个区块各跑一遍 = 同一队列被反复走 18 遍。

| 玩家口径（四档过线） | **49–50 / 48** | 49–50 | 58–82 | 四档全胜 |

两个败因各配一个杠杆，**两项都做**（用户指令）。

### 11.1 分派规则：小突变交回异步路径（**做了两版，都被测量否定，默认关**）

- **起因**：`sky_hole` 每 pass 只有 25 次改动，而就地通道要付 `setupCaches` + 播种 + 统一衰减的**固定**开销（1.00 ms）；底座的一条异步任务只要 0.86 ms。也就是说就地通道有个**突变规模下限**。
- **第一版**（`scalablelux.inlineMinBurst`，缓冲总数 ≤ 阈值 32 就全部交回 `lightQueue.queueBlockChange`）：
  单光源档 3 轮交错 A/B 读出 **0.733 / 0.956（关）/ 0.993（底座本体）ms**，看着像赢。
- **但它在验收跑里当场炸了**：6 轮三侧验收 #2 的第 1 轮，`block_toggle_border` 从 0.43 ms 变成 **4.03 ms**——那 95 次改动是按区块小块到达的，**每一小块都被当成独立异步任务**，于是把"完成路径等待"整笔重新付了一遍。这是本档 8.4× 的倒退，而它恰恰是我们最好的那一格。
- **第二版**（加"只在整个突变落在同一个区块里"的条件 —— 一个区块 = 一个异步任务）：专门 A/B 两档 × 3 轮：

| | 规则开（同区块） | 规则关 |
|---|---|---|
| `block_toggle_border` | **3.97 ms**（4.08/3.97/3.76） | **0.47 ms**（0.67/0.47/0.43） |
| `sky_hole` | 0.754 ms（0.754/1.539/0.736） | 0.777 ms（0.734/0.777/1.054） |

  ⇒ border 的突变**本来就是同区块的**（假设错了），保护不了；而 sky_hole 两版之间**没有可靠差别**——第一版那个 0.733-vs-0.956 是轮间噪声，不是规则的效果。
- **结论**：真正的判据是**每次改动的成本**（border 约 4.5 µs/次，sky_hole 约 22 µs/次），而它只有在活干完之后才知道，运行时无法预判 ⇒ **规则关闭**（`inlineMinBurst` 默认 0），代码与这段记录留在树里。

### 11.2 批量重算：区块级 `lightChunk`（**判负，关闭**）

- **起因**：structure 的 4096 次改动是**逐条播种**（约 1.16 µs/次）；1.x 靠批量重算摊销。
- **修法**：`scalablelux.bulkRelight`（默认关）+ `bulkMinChanges=128`。同一区块一次缓冲 ≥128 条改动时，改成对该区块做**一次完整 `lightChunk`**（区块加载用的同一例程，正确性来自底座）。
- **实测**（3 轮交错，两档都开就地通道）：

| 场景 | 关 | 开 |
|---|---|---|
| `structure_cube` | **5.53 ms** | 6.42 ms |
| `dense_chunk_patch` | **3.88 ms** | 3.95 ms |

- **判断**：一个区块的完整重算 = 24 个 section 的全部格子（约 98 k 格），**远比 4096 次播种贵**。指纹两档逐位相同（`sky=905931078dfc5ace block=59e2252f732ce67b`）说明它至少是**正确**的，只是更慢 ⇒ 开关保持默认关，代码留在树里但**不武装**（分支是 `static final false`）。
- 由此得到一个反向结论：**"批量重算"这个思路只有在"被改动的格子数 ≈ 区块总格子数"时才划算**；structure 只改了 4096/98304 = 4%，所以逐条播种才是对的。

### 11.3 成本地板重新标定：structure 到底输在哪

同一批 jsonl 里的每改动成本（ns/change）：

| 侧 | apply 段 | wait 段 | 每 pass 合计（约） |
|---|---|---|---|
| 新路径（就地） | 1164 | 578 | 1742 |
| 2.0 基线（底座异步） | 606–665 | 609–856 | 1215–1520 |
| 1.x | 634–636 | 162–208 | 796–844 |

- **apply 段的 ~600 ns/改动是底座自己"只入队"时的地板**（连排队都要付）。所以在结构档上，我们的就地路径和底座异步路径落在同一个数上：验收 #1 中位数 **4.88 vs 4.84 ms（打平）**；11.2 那个 A/B 里的 5.53 vs 4.93 是脏窗口噪声，不是批量重算的功劳。
- **1.x 的 2.95 ms 来自它的稠密区域图像**：apply 与底座同价，但 wait 只有 170 ns/改动（我们 578）。这是"SL 系引擎拿不到的那半边"——不是实现问题，是**引擎形态的差**（区域图像是 1.x 独有的，见本文件 §2 的成本地板）。
- ⇒ **structure 这一格不是缺陷，是地板**：SL 系引擎在"4096 次改动挤在一个 section"这个形状上就是 ~4.9 ms。

### 11.4 刷新缓冲大小（256 / 1024 / 4096）：**无效，关闭**

- **起因**：structure 每 pass 的 4096 次改动是按 256 一刷（16 次），每次刷新都要付 `setupCaches` + 播种 + 一次统一衰减的**固定**开销 ⇒ 怀疑那 16 次刷新的固定成本就是结构档的缺口。
- **实测**（两侧 2 轮，同一 jar，只换 `scalablelux.pendingFlushSize`）：

| 场景 | 256（现状） | 1024 | 4096 |
|---|---|---|---|
| `structure_cube` | 4.60 / 5.03 | 4.65 / 4.51 | 5.68 / 4.61 |
| `dense_chunk_patch` | **1.32 / 1.29** | 1.42 / 1.42 | 1.46 / 1.46 |

- **判断**：structure 两轮之间的离散度（±0.5 ms）比三个设置之间的差别还大 ⇒ 没有效果；dense 反而**一致更差**（256 最好）⇒ 维持 256。六次运行的光照指纹全部逐位相同，所以更大的缓冲也没有把工作偷偷推到测量之后——它只是什么都没买到。**这也反过来说明了结构档的成本不在"刷新的固定开销"上，而在每次改动本身的播种/传播上**（见 §11.3 的地板表）。

### 11.5 跑测卫生（这次踩到的两个坑）

- **基准服的端口是 25665–25668**（vanilla 25665 / scalablelux 25666 / lucistarlink 25667 / generator-accelerator 25668），不是 25565。一个卡住的旧 JVM 占着 25666 时，**该目录下每一轮都在加载阶段 `BindException` 死掉、而 gradle 仍然退出码 0** —— 唯一的迹象是 harness 不打 `LUCIS_BENCH_METRIC`、jsonl 不生成、脚本行读成 `minPass=NONE`。因为 `new` 与 `base` 共用 scalablelux 目录而 `ls1` 有自己的目录，这个故障的签名是**「new 和 base 一起失败、ls1 正常」**，要按端口/卫生问题读，不要当成引擎回归。
- 杀进程：`Stop-Process -Force` 打在「bash → java」这对进程上会**静默失败**（进程还在），`cmd //c "taskkill /F /T /PID <pid>"` 才能可靠地连树一起杀（Git Bash 会把裸 `/F` 篡改成 `F:/`，`cmd //c` 能挡住）；单个 java 仍然用 `Stop-Process`。另外脚本某一行报错后**会继续往下跑**（`set -uo pipefail` 没有 `-e`），所以"启动过两次"会留下两个实例抢同一个 run 目录并把输出交错写进同一个日志——用 `CommandLine -match 'zcode-<名字>\.sh\s*$'` 才能准确数出实例数（关键词过滤会把我自己的 shell 也数进去）。

## 13. structure_cube 为什么输：把这一格的每一纳秒摆出来（2026-09-22 深夜）

用户问「引擎怎么输了」。这一格不能只回答"地板"，要把钱花在哪里算清楚。四个侧同一条结构档、同一套协议：

| 侧 | minPass | apply 段 | wait 段 | 每改动 |
|---|---|---|---|---|
| **原版（无光照模组）** | **13.40 ms** | 775 ns/次 | 2874 ns/次 | 3702 ns |
| 2.0 基线（底座异步） | 4.94 ms | ~640 | ~730 | ~1370 ns |
| **新路径（就地通道）** | 5.01 ms | 1164 | 578 | ~1740 ns |
| **1.x（Lucis）** | 2.86 ms | 634 | ~185 | ~820 ns |

**4096 次改动的 apply 段，四条路都在 600–775 ns/次**——这就是 `Level.setBlockState` 自己的账（状态写入 + 高度图 + 脏标记 + vanilla 的同步 `checkBlock` 光照钩子 + harness 的循环开销）。1.x 的 **2.86 ms 里约 2.6 ms 就是这个地板**，它自己的光照工作只剩 ~0.26 ms。**换句话说：这一格 90% 的读数在量 Minecraft 本体，不在量光照引擎**，而 1.x 已经贴着那堵墙站着。

### 13.1 我们那 2.3 ms 花在哪（同一次 profiler 跑，单 pass 实测）

`ownEditCalls=4119 / ownEditBatched=4120`（约 20 次刷新调用承载 4120 次改动）：

| 段 | 实测 | 说明 |
|---|---|---|
| `setupCaches` | 0.09 ms | 建缓存（20 次调用） |
| **`propagateBlockChanges`** | **1.94 ms** | **81% 在这里，其中天空引擎 2.30−0.09−0.04 ≈ 2.16 ms** |
| `updateVisible` | 0.04 ms | 可见层发布 |
| `decBatchNanos` | 0.18 ms | 方块光统一衰减 |

再往里，BFS 的**格子账**（新增计数器，`-Dscalablelux.profile` 才计数）：

- `skyColumnCells=4096` —— 天空光列下降只走了 **4096 格**（256 列 × 16 格/列，立方体内部不透明、走几格就断）
- `bfsPops=24385` —— 增长队列处理了 **2.4 万条队项**
- `bfsNeighbours=52669` —— 队项一共**检查了 5.3 万个邻居格**（约 2.2 个/队项，不是 6 个：其余邻居落在未加载 section 上）
- **`bfsLevelSkip=43789`** —— 其中 **83% 是"已经是这个等级 / 未加载"的即跳**，真正干活（取方块状态、可能写入）的只有 8,880 次
- `skyWrites=10766` —— 实际写 1.08 万格

⇒ **1.996 ms ÷ 52669 ≈ 38 ns/邻居格**（含 profiler 自身约 +5 ns 的计数开销）。这个数一开始看着像"nibble 读太贵"，但查过 `SWMRNibbleArray.getUpdating(index)` 本身只是"取字段 + 取数组 + 位运算"，约 2–4 ns。38 ns 花在**两级指针追逐**上：`nibbleCache[sectionIndex]`（section 引用数组，随机访问）→ `SWMRNibbleArray` 对象 → `storageUpdating[]`，每个邻居格两次 cache 未命中级别的跳转，再叠上分支预测失败。**这才是 Starlight 存储的单价**：每个被摸到的格子 ~35 ns。

### 13.2 1.x 为什么只有 0.26 ms

1.x 把光照放在**一整块平坦的字节图像**里（每格一字节、区域级连续内存）。同样 5.3 万次格子触达，没有指针追逐、可以预取，单价 ~3–6 ns ⇒ **5.3 万 × ~5 ns ≈ 0.26 ms**，与它实测的 0.26 ms 对得上。它的天空光也确实是按列算的（heightmap 驱动），但**决定性的是存储形态，不是列不列**：Starlight 的 35 ns/格 与平坦图像的 5 ns/格 差 7 倍，正好是我们这 1.94 ms 与它那 0.26 ms 的差。

⇒ 这也推翻了我一开始的判断（"先把算法形状改对，再谈存储"）：**形状不是主因，存储是**。5.3 万次触达里 83% 是即跳，就算把算法换成列规则、把队项砍到 256，只要存储还是逐格追指针，省下来的也只是那部分即跳，而它们本来就是最便宜的部分。**

### 13.3 因此这一格的**上限**是可算的

- 地板（原版 setBlockState + vanilla 光照钩子）：**2.5–3.2 ms**
- 1.x：**2.86 ms**（地板 + 0.26）
- 该格可达到的理论最好：**~2.6–3.0 ms** ⇒ **相对 1.x 最多赢 5–15%，而这是"我们的光照工作为 0"才有的数**

所以我们输的这 1.75 倍里：**约 2.0 ms 是我们的天空 BFS 用错了形状的算法**（列状改动却走六邻域 BFS），**约 2.6 ms 是原版自己、谁也拿不走**。前者可以抢回来大部分（预期 5.01 → ~3.0–3.5），后者决定了这一格**不可能出现大比分胜利**。

### 13.4 下一步：R5 ＝ 把光照真值换成**平坦字节图像**（这才是计划里没落地的那一半）

§13.1/13.2 的证据把靶子定死在存储上：**5.3 万次触达 × (35 ns − 5 ns) ≈ 1.6 ms 是可以抢回来的，而抢它只能靠换存储形态**。R5 的范围：

1. **光照真值**：每格一字节的 sky / block 平坦图像（区域级连续内存），替掉"逐 section 的 `SWMRNibbleArray` + `nibbleCache[]` 指针追逐"；
2. **材质**：不透明度/遮挡以每格一字节并行存，**按改动增量维护**（只在格子变化时更新），不做整 section 提取——这是 own-engine v1 死掉的那 45 ns/格，必须绕开；
3. **传播**：在平坦图像上跑 BFS（增加/衰减），保留 Starlight 的语义（含遮挡形状、条件不透明）；
4. **接口**：安装/发布、区块生命周期、存档/重启、worldgen 全部沿用现有那层（它们已经过了 G1/G2 闸门）。

**预登记熔断（R5）**：`structure_cube` 6 轮中位数 ≤ 2.86 ms 且 border/dense/sky_hole 不劣化、规范指纹一致、四阶段无挂死 → 保留；否则撤回，并把这一格定性为**"读数 90% 来自原版 `setBlockState`，不可竞技"**，对外材料（README/对比表）必须标注这一格的口径。

**上限要先说清楚**（避免又一次"以为能大胜"）：structure 的**地板 2.5–3.2 ms 是原版自己的**，1.x 的 2.86 ms ≈ 地板 + 0.26。所以 R5 成功后最好也就是 **~2.9 ms，即与 1.x 打平或胜在噪声内**；这一格**不可能出现 2 倍级胜利**，因为一半以上的读数根本不经过光照引擎。真正量到引擎的三格（border 1.7×、dense 1.8×、sky_hole 噪声）我们已经在赢或平。

## 14. 列扫描探针：**它把"只改算法"这条路也否掉了**（2026-09-22 深夜）

`OwnSkySweepProbe` 由 harness 在**指纹稳定之后**（不在测量窗口内）反射调用，覆盖同一个规范箱 `-40,32,-40..55,96,55`，读的是与指纹同一层的光照。实测一行：

```
SKYSWEEP-PROBE box=-40,32,-40..55,96,55 columns=9216 cells=599040 inRun=295381 inRunMismatch=0
               belowRunNonZero=101055 unknownOpacity=0 probeNanos=62356500 nsPerCell=104
               ruleCoveragePct=49 fixupCells=303659 fixupCostEstNanos=9717088
```

- **列规则本身是精确的**：它判定为"15"的 **295,381 格（49%）里，与引擎不一致的是 0 格**。也就是说"从世界顶往下、直到第一个不能证明透明的格子"这条规则，凡它敢下结论的地方都对（`unknownOpacity=0`，本档所有方块状态的不透明度都是热的）。
- **但它只覆盖一半**：箱内 **101,055 格（17%）需要真正的三维传播**（规则给 0、引擎非 0——悬挑/立方体下方的侧向光），另有约 20 万格规则给 0 且引擎也是 0（这些不需要任何工作）。
- **关键否证**：一轮完整的列扫描要覆盖 **599,040 格**；就算按平坦数组的乐观单价 2.5 ns 算也是 **~1.5 ms**，与现在 BFS 的 1.7 ms 基本同价——**"只把天空光换成列扫描"救不了这一格**。探针自己那份 `nsPerCell=104` 还额外说明了：走公开 API（`getBlockState` + `getLightValue`）的朴素扫描比平坦数组慢 40 倍，所以**平坦存储是任何便宜扫描的前提，不是它的替代品**。

### 14.1 于是 R5 的两个乘数，各自单独都不够

| 乘数 | 实测 | 单独能到 |
|---|---|---|
| 平坦字节存储（每格一次寻址，无两级指针追逐） | 隔离测量 **3.0×**（3 ns → 1 ns） | 1.70 ms → ~0.6 ms ⇒ structure ~3.9 ms |
| 少摸格子（只有 2× 量级靠算法重构能拿到） | 列扫描覆盖 49%、17% 必须三维 | 单独无收益（§14 第一行） |

两个乘数合起来才可能接近 **~2.9 ms**（即打平 1.x），而这就是"完全自研引擎"里**还没落地的那一半**：自有平坦存储 + 自有更新循环——不是"改个算法"，是把 R4 那层更新路径整体挪到自有数据上。**熔断不变**（§13.4）：6 轮 structure ≤ 2.86 ms、其余三格不劣化、指纹一致、四阶段无挂死；否则撤回并把这一格对外标注为"读数主要来自原版 `setBlockState`"。








## 15. 平铺镜像第一版：实测慢 6000 倍，原因定位到"归属"（2026-09-23 凌晨）

R5 的下一半（把传播热路径从"逐格追 nibble 指针"换成"读平坦字节表"）写出来了：在 `StarLightEngine` 里给每个 section 缓存槽配一份 `byte[4096]` 镜像，四个 BFS 循环的读取改走镜像、每次写入写穿（`-Dscalablelux.flatLight=true`，默认关）。

**实测（structure_cube，指纹随跑）：**

| | 单 pass | 结果 |
|---|---|---|
| 关（现状） | **4.6 ms** | 指纹 `sky=905931078dfc5ace block=59e2252f732ce67b` ✓ |
| 开（镜像） | **27.8 s → 322 s**（还在涨） | 日志 `Can't keep up! Running 27778ms behind`，被 420 s 超时杀掉 |

**不是结果错了，是每格都在重建。** 镜像按**引擎的缓存槽位**归属，而这些槽位是跨区块、跨刷新复用的：身份校验几乎每次访问都失败 → 每次失败重建一个 4 KB section（4.5 µs）并新分配一块内存 → 重建风暴。**结论：镜像必须归"光照数据自己"（挂在区块的 nibble 持有者旁边、按 section 一次建好），而不能挂在会被回收的缓存槽上。** 这个绑定就是 R5 的存储搬迁本体。

代码与这条记录留在树里（默认关，注释里写明"开它会慢 6000 倍，别开"），因为它就是"还没落地那一半"的第一块，也是复现这条测量的最快方式。§13.4 的熔断不变。

## 16. 归属修好之后的平坦镜像：**正确，但一致更慢 —— 关闭**（2026-09-23 凌晨）

按 §15 的结论把归属改对：镜像挂到**区块自己**（`ExtendedChunk.scalablelux$getSkyFlat()` / `getBlockFlat()`，随 nibble 数组一起分配、一起丢弃），引擎的每个缓存槽只复制一个**引用**（`flatBound(slot)`），每个 section 的 4 KB 展开只在**第一次被摸到**时做一次并存回区块。重建风暴随即消失：不再有 `Can't keep up`，四轮全部正常跑完。

**实测（structure_cube，开关 A/B，指纹随跑）：**

| | r1 | r2 | 指纹 |
|---|---|---|---|
| 关（nibble 现状） | **4.47 ms** | **4.89 ms** | 规范值 ✓ |
| 开（区块持有的平坦镜像） | 6.29 ms | 5.27 ms | 规范值 ✓ |

**两侧指纹都是规范配对**（`sky=905931078dfc5ace block=59e2252f732ce67b`）⇒ 镜像**语义完全正确**；但**慢 8%–40%，两轮区间不重叠**（关的最大 4.89 < 开的最小 5.27）⇒ 判负。

**为什么否定的是"字节表"而不是"平铺"这件事本身**：nibble 读本来就只要 3 ns（隔实测），换成字节表只省掉指针跳转的一小部分；代价是**热工作集翻倍**（4 KB/section 对 2 KB/section，25 个 section 就是 100 KB 对 50 KB），加速缓存压力加上写穿的额外一次存储 —— 收支为负。**所以 1.x 的优势既不是"nibble 还是字节"，也不是"找路"，而是它根本不做这种 BFS**：它的 0.26 ms ≈ **一次 98,304 格的线性重算 × 2.5 ns**。

⇒ R5 的下一步只剩一个形态：**对"被改动的那一（几）个区块"做一次自己的线性天空光重算**（顺序写、不随机读），而不是让 24,385 个队列条目去铺开 BFS。§14 的列扫描探针已经证明"覆盖整个箱"不行（59.9 万格），但"整区块重算"是 9.8 万格——正好是 1.x 的量级。平坦数组在这里的角色也跟着变了：它不是"给 BFS 当读缓存"（已判负），而是"线性重算的落盘格式"。

## 17. 材质表：快 ~10%，但**正确性不过 ⇒ 拒绝**（2026-09-23 凌晨）

按"每次查方块状态 20 ns × 8,790 次/pass"这条账，做了**逐格不透明度表**（`ExtendedChunk.scalablelux$getMaterial()`，`-Dscalablelux.materialTable=true`）：按 section 建一次、方块改动时置空重算，热循环里把 `getBlockState` + 取 opacity 换成**一个字节读**。

**实测（structure_cube，A/B，指纹随跑）：**

| | r1 | r2 | 指纹 |
|---|---|---|---|
| 关 | 5.18 ms | 4.79 ms | `sky=905931078dfc5ace block=59e2252f732ce67b` ✓ |
| 开 | **4.60 ms** | **4.34 ms** | `sky=ca5a897d43d2543d` / `sky=54c3a7a9b6b518c4` ✗（两次还不一样） |

**速度方向是对的（约 −10%，正落在预测的量级上），但光算错了，而且不稳定 ⇒ 按闸门拒绝，开关保持关。**

**原因（诚实结论）：失效信号的覆盖面不够。** 我们只在引擎自己的方块改动入口（`blocksChangedInChunk`）里置空表项，但方块还会被**不经过我们**的路径改掉——worldgen 直接写、`sectionChange` 的空/非空转换、以及任何直接写 palette 的代码。表一旦在这些路径之后继续被信，就会用旧的不透明度去传播 ⇒ 光错。**这不是实现疏漏，而是"引擎不拥有数据"的必然结果**：只要方块数据的唯一真值在别人的 palette 里，就没有一个便宜且可靠的"版本戳"能告诉我们它变了。要修就得把所有写路径都接管（即 own-engine 那条已经因 45 ns/格被否掉的路）。

⇒ 这一条连同 §11–§16 一起，把**所有增量杠杆逐个关上**：批量重算（慢）、分派规则（把 border 打崩）、刷新缓冲（无效）、字节表当读缓存（慢）、缓存槽归属（重建风暴）、列扫描（无收益）、材质表（快但错）。

## 18. 材质表 + 可靠的 dirty 信号：**正确了，但变成慢 11% —— 那个"快 10%"是假的**（2026-09-23 凌晨）

按 §17 的判断，把失效信号从"引擎自己的改动钩子"换成**方块写入的唯一漏斗**：`LevelChunkSection.setBlockState` 挂 mixin（两个重载都挂，显式描述符——只写方法名会被 Mixin 判成 `Invalid descriptor` 并让整个游戏起不来，这个坑当场踩了一次），每个 section 一个 `scalablelux$materialDirty` 位；引擎**每个槽位每次调用只校验一次**（section 身份 + dirty 位），重建时清位。

**实测（structure_cube，A/B，指纹随跑）：**

| | r1 | r2 | 指纹 |
|---|---|---|---|
| 关 | **4.55 ms** | **4.75 ms** | 规范值 ✓ |
| 开 | 5.28 ms | 5.23 ms | 规范值 ✓ |

**两边指纹全部规范 ⇒ 信号是对的、表是对的**（这是本轮的验收点）；但**慢约 11%**（区间不重叠）。

**关键结论：§17 那个"快 10%"不是优化，是"算错了所以干得少"。** 不正确的表让传播提前收敛（拿到旧的/错的不透明度 ⇒ 更少的写入与扩张），于是读数看起来更好。修正之后真相是：**材质表在这个引擎里是负收益**——省下的 20 ns × 8,790 次，抵不过每次校验/重建与维护 dirty 位的开销。

⇒ 材质表连同 §11–§17 **全部关闭**。到这一步，structure_cube 的每一个增量杠杆都已被测量并附上原因：
批量重算（慢）、分派规则（打崩 border）、刷新缓冲（无效）、字节表当读缓存（工作集翻倍）、缓存槽归属（重建风暴）、列扫描（同价）、材质表（假快真慢）、材质表+可靠信号（真慢）。

## 19. 决定性一格：平坦数组上"扫一格"= 2 ns，一个区块 0.197 ms（2026-09-23 凌晨）

探针补上了**纯数组**的扫描计时（同一批方块/光照缓冲，不经过 `getLightValue`/`getBlockState`，只做顺序读写）：

```
flatSweepNsPerCell=2   flatSweepOneChunkNanos=196608（=0.197 ms / 98,304 格）
（对照：走公开 API 的同一条规则 nsPerCell=114 —— 慢 57 倍，§14）
```

⇒ **1.x 的 0.26 ms 在原理上被复现了**：它就是"一个区块 9.8 万格 × ~2.5 ns 的线性重算"。而**平坦存储是这条路的前提**（§14 已证：走 API 的扫描永远慢 57 倍）。

**但把这笔账算完，结论仍然是"追不上"**，这就是我把它记在这里的原因：

| 项 | 预估 |
|---|---|
| 一个区块的列扫描 | **0.20 ms**（实测） |
| 修正 BFS（规则覆盖 49%，其余 17% 需要三维；区块内约 3k 非零格 × ~50 ns + 邻格触达） | ~0.35 ms（估算） |
| 材质表构建（24 section × 4.5 µs，每次重算一次） | ~0.11 ms |
| **合计** | **~0.66 ms**，对现状 1.70 ms ⇒ structure **5.01 → ~4.0 ms** |

**仍落后 1.x 的 2.86 ms 约 1.4 倍**——因为那只省掉 1 ms，而另外 2.6 ms 是原版 `setBlockState` 的账。

### 19.1 结论（本项目对 structure_cube 的最终定性）

- 9 个增量杠杆全部实测并关闭（§11–§18），每个都带原因，没有一个是"还没试"。
- 唯一未走的路（自有平坦存储 + 线性重算）**已有实测支撑**，但它的完整账算下来是 **~4.0 ms，仍落后**，而开发量是本项目里最大的一次（自己拥有更新循环，且要解决世界/区块生命周期的所有失效点）。
- **因此我的建议是：structure_cube 就此收口**，把力气放在已经赢的两格（border 1.7×、dense 1.8×）、玩家口径（四档全胜：50 ms vs 60–107）以及对外材料上——那一格胜负的天平上压着 2.6 ms 的原版开销，无论怎么做都赢不了大分。
