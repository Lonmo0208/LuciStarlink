# 新架构前置：两家引擎的层级拆解与吸收清单

* 指令：用户，2026-09-22（「完全自研新架构 糅合两种架构的优点」「一层一层的细细解开 吸取全部优点」「全方面碾压两位前辈模组和1.x」）
* 本文是**新引擎的项目输入**：逐层对比 `2.0（ScalableLux 底座 + 我们的层）` 与 `1.x（Lucis 系区域引擎 + 我们的加固）`，标出每层的做法、实测代价、谁更强、以及新架构应吸收哪一边。
* 配套：`OWN-SCHEDULER-PLAN.md`（12 次尝试与四次挂死的定性）、`OWN-INSTALL-PLAN.md`（成本分解）、`lucistarlink-engine-metric-border`（记忆中的台账）。

## 0. 新引擎必须同时满足的硬约束（前序工作换来的）

1. **当场算完**（否则任何等待者都会与延迟互锁——四次挂死分别落在四个阶段证明了这点）；
2. **拥有自己的光照真相**（否则"待处理"状态必然存在，1 无法成立）；
3. **但发布面必须与别人一致**：原版读的就是 chunk section 里的 nibble 数组（客户端发包、存档、其它模组），所以安装必须写回同一批数组（1.x 也是这么做的）；
4. **正确性契约不可退**：安装同时写 updating + visible（1.1.5 的教训）、跨区减光不截断（1.2.9）、重启不截断、worldgen 自然光与原版一致（1.2.7）；
5. **活性**：任何"持有/排队"都必须有**保证会发生**的排空点；本次证明了"保证"很难凑齐 ⇒ 新引擎的设计目标应是**不持有**。

## 1. 层级拆解

| # | 层 | 2.0（SL 底座 + 我们） | 1.x（Lucis 系 + 我们） | 谁强 / 新架构取谁 |
|---|---|---|---|---|
| L1 | **光照真相** | 原版 `DataLayer`（section 内 nibble），引擎只读写 | **自己的区域图像**（region images）为算，结果发布到原版数组 | 1.x 的**算用自有、存用原版**是唯一能"当场算完"的形态 ⇒ **取 1.x 形态** |
| L2 | **编辑入口** | `blockChange` → 队列（`ChunkTasks`+票据），完成在后 | 同步发布通道（`directSectionInstall`+`syncRuntimeDrain`），**调用内安装** | **取 1.x**（必须当场） |
| L3 | **传播算法** | 逐格增量 BFS（每改动 0.3–0.65 µs；每 pass 全部传播 23–30 µs） | 区域重算 + 均匀光源跳过 + 精确双队列天空光修复 | **两者都取**：小改动走增量（SL 便宜），批量改动走区域摊销（1.x 便宜）——**这是"批量通道"的设计依据** |
| L4 | **安装/发布** | 脏 section 只发一次（我们加的"内容未变不发通知"） | 脏 section 发布 + halo/跨区发布 | **取 1.x 的直装语义 + 我们"内容未变不发"的过滤** |
| L5 | **客户端同步** | 每层一个 BitSet、每 chunk 每 tick 至多一包、空层零负载（实测已最小） | 1.2.5 的 −51% 老问题已在新底座上不存在 | **取 2.0**（现状即最优，别再优化它） |
| L6 | **调度与活性** | 光照线程 + 队列（底座）= 活性保证，但带来完成延迟 | 自有 worker + 区域作业；同步通道绕开队列 | **新架构：不排队 ⇒ 不需要"光照线程"这个活性保证**；批量与世界生成仍用 worker 池 |
| L7 | **区块生命周期** | 票据 / `ChunkTasks` / `onComplete` 把"区块别卸载"和"完成"绑在一起 | 区域 init/adoption-backed 初始化 | 新架构需要**显式的区块引用计数**（谁在用、何时可卸载），这是 L1 自持的代价之一 |
| L8 | **存档/重启** | 原版两钩子（append unsaved lighting / force light incorrect before save），审计为等价或更强 | 1.1.5 重启修复、1.2.9 跨区减光修复 | **取两家并集**（审计结论 + 我们两个真实缺陷的修复） |
| L9 | **worldgen** | `WorldGenRegionMixin` 未点亮前返回 0；异步队列 | PR#1 worldgen 自然光修复；已知 80 格缺陷（我们的 bug） | **取 2.0 的路径 + 1.x 的修复经验**；80 格缺陷必须在新引擎里不复现 |
| L10 | **配置/兼容/可观测** | 配置面 + Sable 门控 + `/lucistarlink stats\|light\|relight` + `SLTELEM`（我们加的） | 25 键配置 + Sable + 内存遥测 | **全取我们这一层（两边都是我们写的）** |
| L11 | **测量基础设施** | 按-pass 探针、箱内判据、契约协议（本次建成） | 同 | **全取**，并作为新引擎的验收工具 |

## 2. 已知成本地板（新引擎的设计预算）

| 量 | 实测 | 出处 |
|---|---|---|
| 单格增量传播 | **0.3–0.65 µs/改动** | 本分支 M2-2 |
| 一个区域/一批的作业（含取还） | **250–600 µs/批** | 1.x runtime 队列 |
| 1.x 一次 pass 的区域口径 | **1.26–3.4 ms**（拆/放档） | 6 轮校准 |
| **材料交付（own-engine v1 的死因）** | 逐格 536–2808 µs → 调色板 API **375–1071 µs（≈45 ns/格）**；乐观组合 ≈48 µs/编辑 vs SL ≈34 µs | `OWN-ENGINE.md` |
| own-engine v1 核心（原地传播，逐格验证正确） | **13.4 µs/编辑** | `OWN-ENGINE.md` |
| 2.0 每 pass "能摸到"的总量（拆/放档） | 入队 30–123 µs + 传播 23–30 µs + apply ~172 µs | 本次成本分解 |
| 2.0 完成延迟（同一格剩下的） | **≈4.3 ms** | 本次 |

**预算结论**：新引擎的每次编辑预算 ≈ 1.x 的 1.26 ms / 95 改动 ≈ **13 µs/编辑**；其中**材料/安装不能超过几微秒**——这正是 v1 撞墙的地方，所以 L1 的自有真相必须**按"算的时候就在自己的格子里"设计**（不要再有"从原版数组反抽材料"这一步）。

## 3. 由此确定的新引擎形态（初稿）

```
编辑(服务器线程)
  └─ 自有光场（每 section 一份 nibble，与 ID 映射表）
       ├─ 单格增量传播（SL 的算法，0.3–0.65 µs）
       ├─ 批量：同一 section 内 ≥K 个改动 → 一次分区重算（1.x 的摊销）
       └─ 安装：直接写回该 section 的原版数组（updating+visible）+ 标脏
  └─ 通知：脏 section → 合并 → 每 chunk 每 tick 一包（L5 现状）
  └─ 完成：本地（无队列、无 future）
批量/世界生成/区块加载：worker 池（保留活性），但它们的完成与"编辑完成"解耦
```

**与 own-engine v1 的关键差别**（v1 死于材料交付）：
* v1：编辑 → 需要材料 → **从原版数组反抽 4096 格** → 太贵；
* 新：编辑 → **自己的光场就是材料**（自持 nibble）→ 只碰受影响的格子 → 无"抽取"这一步。
⇒ **自持 nibble（不是区域图像）** 是 v1 与本次设计的分水岭，也是这次可能成功的原因。

## 4. 里程碑与熔断

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **R0**（本文） | 层级拆解 + 预算 + 形态定稿 | 本文档 |
| **R1** | `OwnLightField`：自持 nibble + 与 section 的双向同步 + 逐格对照测试（对原版/对 SL 两种基准） | 逐格一致（差分探针）；单格增量 ≤1 µs |
| **R2** | 编辑通道：`blockChange` 内传播 + 安装 + 本地完成（开关默认关） | 拆/放档 minPass ≤1.5 ms；指纹一致；**无挂死（四阶段全过）** |
| **R3** | 批量通道：同 section 多改动一次重算 | structure/dense ≤ 现值的 90% |
| **R4** | 全量验收：四档 × 两窗口 × 两口径 + 存档往返 + worldgen 指纹 | 两口径全绿 |

**熔断（任一条不过即回退到 2.0）**：R2 的四阶段无挂死 + 拆放 minPass ≤1.5 ms；四档玩家口径不回退（≤+5%）；指纹与标准值一致；存档/重启光照正确。**且必须逐里程碑验收，不做"一次性大重写"**（V2/V3/own-engine 的教训）。

## 5. 时间与风险（说清楚，不粉饰）

* 这是**数周级**的工程（R1 一项就要把自持光场与两个基准逐格对齐）；
* 前科：own-engine v1（熔断）、V2（前提被否）、V3（三种变体全否）；
* **本次的新意**：自持 nibble 而不是区域图像 ⇒ 绕开了 v1 的材料交付死因；且验收工具（差分探针 + 按-pass 探针 + 箱内判据）已经在手，能逐里程碑证实/证伪。

## 6. 下一步（R1 的第一件事）

`OwnLightField` 的骨架 + **双向同步的正确性测试**：
1. 从 section 的 `DataLayer` 读入 → 自持场（逐格相等）；
2. 自持场改动 → 写回 section（逐格相等，且 updating/visible 都写）；
3. 与 SL 引擎对同一编辑的结果逐格比对（差分探针）。
**这一件事做成，后面才有意义；做不成（例如同步成本太高），按熔断在 R1 就停。**
